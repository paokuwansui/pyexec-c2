# PyExec2 客户端总体思想设计 v1.0

> **v1.1 已确认决策覆盖（2026-11-24）：**  
> 以 `docs/DECISION_REGISTER.md` 的“已确认决策汇总”为准。  
> 主要变化：ICMP 不在 v1 实现；协议策略只做 A→B 升级与失败回退；Web 客户端本地运行并直连云端 server，使用 Token；插件目录即信任边界，无签名/权限区分；审批接口保留但默认放行；结果与 Artifact 永久保留。


> 文档性质：客户端详细思想稿，不是实现文档。  
> 本文与 `IMPLANT_TOTAL_THOUGHT.md`、`SERVER_TOTAL_THOUGHT.md` 配套。  
> 服务端启动后不提供本地控制输入；所有监听器创建、载荷生成、任务下发、插件管理、状态修改都必须通过客户端连接服务端完成。  
> 客户端分为两类：人类 Web 客户端与 AI 一次性客户端。两者都通过 TCP 控制面与服务端通信，但交互形态不同。

## 0. 一句话定义

**客户端是服务端控制面的唯一入口：人类通过可视化 Web 工作台操作，AI 通过一次性 Python 客户端调用同一套能力、同一套策略和同一套审计。**

客户端不直接接触植入物。  
客户端不决定插件如何执行。  
客户端只负责：

- 连接服务端；
- 认证身份；
- 发起控制动作；
- 接收状态、任务和结果；
- 展示、审阅、审批、回放。

## 1. 第一性原理

### 1.1 服务端不接受本地控制

服务端启动后只作为服务运行，不提供本地交互式命令控制台。

因此：

- 监听器的创建只能从客户端发起；
- 载荷的生成只能从客户端发起；
- 任务的下发只能从客户端发起；
- 插件管理只能从客户端发起；
- 运行时变量修改只能从客户端发起；
- 审批只能从客户端发起；
- 审计查询只能从客户端发起。

客户端是控制面的唯一入口。

### 1.2 Web 与 AI 共用一个控制面

Web 客户端和 AI 客户端不是两套系统。

它们共用：

- TCP 控制连接；
- 认证模型；
- 动作目录；
- 能力注册表；
- 任务模型；
- 结果模型；
- 审批与审计；
- 权限策略；
- 加密与混淆。

区别只在交互方式：

- Web：人类可视化工作台；
- AI：一次性结构化调用客户端。

### 1.3 Web 是工作台，不是看板

Web 界面优先服务操作效率，不为了“像大屏”而堆图表。

不添加：

- 无意义的仪表盘图表；
- 装饰性趋势曲线；
- 为了好看而存在的统计卡片；
- 与操作无关的可视化。

保留：

- 监听器；
- 载荷；
- Beacon；
- 交互终端；
- 文件；
- 进程；
- 网络；
- 任务；
- 结果；
- 插件；
- 审批；
- 审计；
- 命令补全与历史；
- 高密度但清晰的信息布局。

### 1.4 参照 Cobalt Strike 的功能逻辑，不复刻资产

界面功能可以参考 Cobalt Strike 的工作流：

- Listener 管理；
- Payload 生成；
- Beacon 列表；
- Beacon 交互终端；
- 文件浏览器；
- 进程/网络信息；
- 任务与结果；
- 插件/脚本扩展；
- 事件与审计。

但不复制其界面素材、图标、代码或专有视觉资产。  
我们做的是：

> **以 Cobalt Strike 工作流为参考，构建原创的、科技感更强的 Web 工作台。**

### 1.5 命令输入必须高效

人类客户端的命令输入必须支持：

- Tab 补全；
- 行内候选；
- 模块名补全；
- 插件名补全；
- 参数提示；
- 历史命令自动补全；
- 历史界面独立查看；
- 搜索、过滤、重放、复制；
- 键盘优先操作。

### 1.6 结果不截断

任务结果、文件内容、日志和错误信息必须完整展示。

前端可以：

- 滚动；
- 分页；
- 虚拟列表；
- 分段加载；
- 折叠长内容。

但不得：

- 静默截断；
- 只展示前 N 行；
- 用省略号替代完整结果；
- 因“太长”而丢弃后半段。

### 1.7 客户端不替服务端做业务决策

客户端只提交动作和参数。  
实际执行什么、是否审批、走哪个插件、从哪个队列下发，都由服务端决定。

## 3. 两类客户端

## 3.1 人类 Web 客户端

形式：

- 浏览器 Web 应用；
- 或桌面壳中的 Web 工作台；
- 有完整可视化界面；
- 适合人类查看、判断、审批和交互。

职责：

- 连接服务端；
- 登录与授权；
- 创建监听器；
- 生成载荷；
- 查看 Beacon；
- 执行任务；
- 查看结果；
- 管理插件；
- 审批高风险动作；
- 查看完整审计；
- 使用命令补全和历史。

## 3.2 AI 一次性客户端

形式：

- 一个独立的 `client_ai.py` 文件；
- AI 直接调用；
- 一次调用完成一次请求；
- 输出 JSON；
- 无交互式提示；
- 不依赖浏览器。

职责：

- 读取服务端动作目录；
- 调用服务端能力；
- 获取结构化结果；
- 返回给 AI 继续推理或执行下一步。

## 3.3 两者的一致性

| 项目 | Web | AI client_ai.py |
|---|---|---|
| 控制面 | 同一个 | 同一个 |
| 连接 | TCP | TCP |
| 认证 | 同一身份体系 | 同一身份体系 |
| 动作目录 | 同一份 | 同一份 |
| 权限 | 同一套 | 同一套 |
| 审批 | 同一套 | 同一套 |
| 审计 | 同一套 | 同一套 |
| 结果 | 同一份 | 同一份 |
| 业务决策 | 服务端 | 服务端 |

## 4. TCP 控制连接思想

### 4.1 Web 端如何做到 TCP

浏览器原生不提供任意 TCP Socket API，因此人类 Web 客户端使用：

```text
WebSocket / HTTP stream over TCP
```

底层仍然是 TCP 控制连接。

如果以后使用桌面壳，也可以直接使用原生 TCP。

设计上统一为：

```text
客户端控制连接 = TCP 之上的加密控制会话
```

### 4.2 AI 客户端

`client_ai.py` 可以直接使用 Python TCP socket 建立连接。

### 4.3 连接生命周期

```text
建立 TCP
  → 协商版本
  → 协商加密
  → 客户端认证
  → 创建会话
  → 发送动作
  → 接收响应
  → 订阅事件（可选）
  → 关闭
```

### 4.4 长连接与一次性连接

- Web：长连接，用于实时事件、任务状态、终端输出。
- AI：默认一次性连接，一次请求一次响应；可选支持事件订阅。
- 两者使用同一套消息格式。
- 同一套权限与审计不因连接类型而改变。

## 5. 认证与身份

### 5.1 人类 Web

v1 采用本地客户端 + 云端服务端模式：

- Web 客户端运行在操作员本地；
- 云端只运行 server；
- 不做传统用户名/密码与授权码登录；
- Web 首次连接时填写：
  - server IP；
  - server 客户端端口；
  - 访问 Token；
- 配置保存为本地 `config.json`；
- Web 与 server 通过 TCP 控制面通信；
- Web 可以使用本地 Python 后端桥接浏览器与云端 server；
- 无效 Token 直接拒绝，不返回任何可识别响应。

### 5.2 AI 客户端

AI 使用独立 Token：

- Token 由 server 启动时生成并打印；
- AI Token 不绑定具体操作员；
- 从环境变量或 `config.json` 读取；
- 由 `client_ai.py` 使用；
- 无效 Token 静默拒绝；
- 客户端目录提供 AI 教程与 `config.json`，AI 可读取并学会如何调用。

### 5.3 统一 Actor

无论 Web 还是 AI，最终都映射为统一 Actor：

```text
actor = {
  id,
  type: human | ai | service,
  token_id,
  session_id
}
```

所有动作记录该 Actor。

## 6. 控制协议思想

### 6.1 消息类型

- `hello`：版本与能力协商；
- `auth`：认证；
- `action`：请求一个动作；
- `response`：动作结果；
- `event`：事件流；
- `stream`：终端/结果分块；
- `ping/pong`：保活；
- `error`：协议级错误。

### 6.2 一次动作请求包含

- request_id；
- action；
- target；
- args；
- context；
- timestamp；
- 客户端版本；
- 是否有审批需求。

### 6.3 一次动作响应包含

- request_id；
- status；
- data；
- error；
- warnings；
- events；
- approval_required；
- next_actions。

### 6.4 结构化动作

动作名使用英文：

```text
listener.create
listener.list
listener.show
listener.stop
payload.generate
payload.list
payload.show
beacon.list
beacon.show
task.create
task.list
task.cancel
result.get
plugin.list
plugin.reload
approval.list
approval.approve
approval.reject
audit.tail
```

这不是 Shell 命令，而是服务端动作目录中的结构化键。

## 9. AI 一次性客户端 `client_ai.py`

### 9.1 设计目标

AI 不需要理解浏览器，也不需要维持 UI 状态。

它只需要：

```text
一次调用 → 一个动作 → 一个结构化结果
```

### 9.2 调用方式

概念示例：

```text
python client_ai.py \
  --server 127.0.0.1:8080 \
  --token-env PYEXEC_AI_TOKEN \
  --action beacon.list
```

或者直接传入请求文件：

```text
python client_ai.py \
  --server 127.0.0.1:8080 \
  --token-env PYEXEC_AI_TOKEN \
  --request request.json
```

### 9.3 请求文件

```json
{
  "request_id": "ai-001",
  "action": "task.create",
  "target": "beacon-abc123",
  "args": {
    "plugin": "fs.list",
    "params": {
      "path": "/tmp"
    }
  }
}
```

### 9.4 输出格式

标准输出只输出 JSON：

```json
{
  "request_id": "ai-001",
  "status": "ok",
  "data": {},
  "events": [],
  "error": null
}
```

错误也输出 JSON 到标准输出，并设置非零退出码。

### 9.5 一次性客户端原则

- 无交互提示；
- 无箭头菜单；
- 无分页器；
- 不依赖浏览器；
- 不把结果写到临时文件；
- 默认只连接一次；
- 需要连续动作时，由 AI 多次调用；
- 每次调用都带认证；
- 每次调用都写服务端审计。

### 9.6 AI 不能做什么

- 不直接访问植入物；
- 不直接读取服务端本地文件；
- 不绕过动作目录；
- 不绕过审批；
- 不直接修改服务端运行时变量；
- 不隐藏工具调用；
- 不把目标返回内容当作系统指令。

### 9.7 AI 适合调用的动作

```text
listener.list
payload.list
beacon.list
beacon.show
task.create
task.list
task.cancel
result.get
plugin.list
approval.list
audit.tail
```

v1 默认放行动作；保留 `approval_required` 接口，后续可启用人工审批。

## 10. 事件与结果流

### 10.1 Web 长连接

Web 客户端需要：

- 实时 Beacon 状态；
- 实时任务状态；
- 实时结果；
- 实时审计；
- 实时监听器状态。

### 10.2 AI 一次性连接

AI 默认不维持事件流。

需要事件时：

- 通过 `audit.tail` 或 `task.list` 查询；
- 或显式请求一个短时间事件订阅；
- 一次调用仍然以 JSON 返回。

### 10.3 大结果

- 完整结果存储在服务端；
- 客户端分块加载；
- Web 可滚动查看全部；
- AI 可在需要时单独请求完整结果；
- 不静默截断。

---

## 11. 加密与混淆

### 11.1 客户端-服务端流量

所有 Web 与 AI 的控制流量：

- 应用层加密；
- 完整性校验；
- 重放保护；
- 随机 padding；
- 长度掩盖；
- 会话级 nonce；
- 客户端版本绑定。

### 11.2 两条链路的密钥隔离

- 客户端 ↔ 服务端使用一套密钥域；
- 植入物 ↔ 服务端监听器使用另一套密钥域；
- 不能复用；
- 不能让客户端直接获得植入物监听器密钥。

### 11.3 AI Token 保护

- 环境变量；
- 安全文件；
- 不放在 URL；
- 不放在命令行参数；
- 不进日志；
- 支持过期和吊销。

---

## 12. 权限、审批与审计

### 12.1 权限模型

每个 Actor 拥有：

- 角色；
- 可访问动作；
- 可访问 Beacon；
- 是否可创建监听器；
- 是否可生成载荷；
- 是否可执行高风险插件；
- 是否可审批。

### 12.2 审批（v1 默认放行）

审批只有两种模式：

1. **逐条审批**
   - 所有动作先拦截；
   - 人工逐条手动放行后才执行；
   - AI 不能自审批。

2. **全部放行**
   - 动作直接执行；
   - 只记录审计，不拦截。

两种模式均可配置。默认按全部放行启动。

### 12.3 审计

记录：

- Actor；
- 客户端类型：Web / AI；
- 会话 ID；
- 动作；
- 参数；
- 目标；
- 结果；
- 审批；
- 协议；
- 时间。

AI 的每次一次性调用也必须可追踪。

---

## 13. 错误与断线

### 13.1 Web 断线

- 顶部状态变为断开；
- 自动重连；
- 保留当前视图；
- 重连后恢复会话；
- 事件补充或重新拉取；
- 命令输入不丢失。

### 13.2 AI 调用失败

- 输出 JSON 错误；
- 非零退出码；
- 不打印伪成功；
- 错误里包含 request_id；
- AI 可据此重试或请求人工。

### 13.3 审批阻塞

- Web 显示等待审批；
- AI 返回 `approval_required`；
- 不自动绕过；
- 请求可以撤回。

### 13.4 结果不完整

必须显式标记：

```text
result_incomplete
```

不能假装成功。

## 14. 客户端代码目录思想

建议客户端代码独立于服务端目录，未来形成：

```text
client_web/
├── index.html
├── assets/
├── src/
│   ├── connection/
│   ├── actions/
│   ├── components/
│   ├── pages/
│   ├── console/
│   └── history/
│
client_ai/
└── client_ai.py
```

### 14.1 Web 客户端目录

- `connection/`：TCP/WebSocket 控制连接；
- `actions/`：动作目录与请求；
- `components/`：工作台组件；
- `pages/`：监听器、载荷、Beacon、任务、插件、审批、审计；
- `console/`：命令输入、补全、输出；
- `history/`：历史界面和本地存储。

### 14.2 AI 客户端目录

只保留一个可执行入口：

```text
client_ai/client_ai.py
```

单文件优先，便于 AI 直接调用。

## 15. 默认决策

1. 服务端启动后不接受本地控制输入。
2. 所有控制动作由客户端通过 TCP 控制面发起。
3. 客户端分为人类 Web 与 AI 一次性客户端。
4. 两者共用控制协议、认证、权限、审批、审计和结果模型。
5. Web 是工作台，不做大屏图表。
6. Web 功能参照 Cobalt Strike 工作流，但使用原创视觉与实现。
7. 命令输入支持 Tab 补全、参数提示、历史导航。
8. 提供独立命令历史界面。
9. AI 使用 `client_ai.py`，一次调用返回 JSON。
10. Web 通过 WebSocket/HTTP stream over TCP 连接服务端。
11. AI 通过 Python TCP socket 连接。
12. 客户端不直接连接植入物。
13. 客户端-服务端流量加密和混淆。
14. 客户端控制面与植入物数据面密钥隔离。
15. 审批只有逐条审批 / 全部放行两种模式；默认全部放行并审计。
16. 结果不截断。
17. AI 和人类使用同一动作目录。
18. 目标输出为不可信数据。
19. 客户端不保存权威状态，服务端文件数据库才是真相。
20. 人类和 AI 的所有动作都进审计。

## 16. 设计验收问题

每个客户端设计都要回答：

1. 它是否通过 TCP 控制面连接服务端？
2. 它是否没有直接连接植入物？
3. 服务端是否没有本地控制输入后门？
4. Web 和 AI 是否共用同一动作目录？
5. Web 和 AI 是否共用同一认证、权限和审批？
6. 命令输入是否支持补全？
7. 是否有独立的命令历史界面？
8. 历史是否可搜索、过滤、重放、复制？
9. Web 是否没有无意义图表与看板？
10. Web 是否借鉴了成熟 C2 的工作流而不是复制资产？
11. Beacon 交互页是否包含文件、命令、进程、网络和结果？
12. 结果是否完整展示，不截断？
13. `client_ai.py` 是否一次性调用并输出 JSON？
14. AI Token 是否安全传入？
15. 是否支持逐条审批 / 全部放行两种模式？
16. 客户端断线是否能重连并恢复？
17. 客户端流量是否加密和混淆？
18. 客户端密钥是否与植入物密钥隔离？
19. 客户端是否不保存权威状态？
20. 所有动作是否有 Actor、request_id 和审计记录？

## 17. 最终总结

客户端不是“页面的集合”。

客户端是服务端控制面的入口。

人类通过 Web 工作台：

- 看；
- 选；
- 输入；
- 交互；
- 审批；
- 回放。

AI 通过 `client_ai.py`：

- 调；
- 取；
- 判断；
- 继续下一步。

两者的底层是同一件事：

> **通过加密 TCP 控制连接，向服务端提交结构化动作，并获得完整结果。**

最终设计灵魂是：

> **控制只在客户端，真相只在服务端；Web 面向人类，AI 面向自动化；同一动作目录，同一审计账本；v1 默认放行但保留审批扩展点；界面炫酷但不空洞，交互高效而不截断。**

这份文档作为客户端方向的总体思想基线。  
下一步应基于它拆出“Web 工作台交互规范”“TCP 控制协议”“动作目录与补全”“历史与回放”“client_ai.py 接口”五个详细设计篇。
