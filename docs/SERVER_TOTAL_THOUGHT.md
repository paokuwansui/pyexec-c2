## 0. 一句话定义

**服务端是一个以文件为持久化底座、以插件为能力扩展方式、以 Python 代码为任务载体、以 TCP 作为客户端接入基础、以多协议监听器连接植入物的能力调度中心。**

它不是：

- 不是把命令写死在代码里的控制台；
- 不是必须依赖数据库的服务；
- 不是必须依赖 Shell/PowerShell 完成任务的管理器；
- 不是单一 TCP 监听器；
- 不是“客户端页面 + 后端接口”的简单 CRUD 应用；
- 不是只能下发任务、不能自我扩展的静态程序。

它是：

- 一个可被插件扩展的服务端运行时；
- 一个文件数据库；
- 一个任务与结果的路由中心；
- 一个协议监听器的宿主；
- 一个载荷生成器；
- 一个面向人类、AI、自动化工具的统一控制面。

## 1. 服务端第一性原理

### 1.1 尽可能插件化

服务端除了维持自身运行所必需的最小核心之外，其余能力都应该被做成插件。

**核心负责“活下去”和“守边界”。**  
**插件负责“干活”和“长功能”。**

这意味着：

- 协议监听是插件；
- 协议载荷生成是插件；
- 任务队列处理器是插件；
- 结果处理器是插件；
- 报表、备份、清理、通知是插件；
- AI 工具是插件；
- Web 扩展是插件；
- 日常运维不应依赖 Shell/PowerShell，而应由 Python 插件直接实现。

### 1.2 能不用 Shell 就不用 Shell

服务端自身也要执行“无必要不 Shell”的原则。

以下行为不应成为默认实现：

- 用 `subprocess` 调 `ls`、`cat`、`cp`、`find`；
- 用 `cmd /c`、`powershell -Command` 做文件或进程管理；
- 用 Shell 管道拼接任务；
- 用外部命令解析 JSON、清理目录、生成报告、备份文件；
- 用外部工具管理监听器或端口。

所有日常能力优先用 Python 标准库或 Python 插件实现：

| 日常动作 | 默认思想 |
|---|---|
| 文件读写 | Python 文件 API |
| 目录扫描 | Python 目录 API |
| 队列处理 | Python 文件队列 |
| 监听器管理 | Python 协议插件 |
| 载荷生成 | Python 载荷生成插件 |
| 进程/端口状态 | Python 系统接口 |
| 报告生成 | Python 模板插件 |
| 备份/清理 | Python 插件 |
| AI 工具 | Python 服务端插件 |
| 客户端会话 | Python TCP 服务 |

### 1.3 文件就是数据库

服务端不依赖 SQLite、MySQL、Redis、MongoDB 等外部数据库。

所有需要持久化的东西，都以文件形式存储：

- Beacon 身份；
- 任务队列；
- 下发记录；
- 回收结果；
- 监听器配置；
- 载荷配置；
- 插件元数据；
- 客户端会话；
- 审批；
- 事件；
- 审计日志；
- 密钥；
- 配置。

文件数据库不是“随便写几个 JSON”。

它必须遵守：

- 原子写入；
- 单写者；
- 目录分片；
- 索引可重建；
- 追加日志；
- 校验与版本；
- 崩溃恢复；
- 文件锁；
- 权限最小化。

### 1.4 服务端也执行插件

服务端不是只会“把代码发给植入物”。

服务端自己也应当：

- 加载插件；
- 执行插件；
- 允许插件访问服务端运行时；
- 允许插件修改运行时变量；
- 允许插件扩展服务端能力。

服务端插件和植入物插件使用同一套核心思想：

```text
运行时全局对象
  + 每次调用的局部命名空间
  + 显式全局修改能力
  + 插件生命周期与注册表
```

### 1.5 启动目录就是工作目录

服务端以启动时所在的目录作为工作目录。

所有相对路径都以工作目录为根：

```text
<startup-directory>/
```

服务端不把状态散落到系统其他位置。  
不依赖用户目录、不依赖当前 Shell、不依赖随机临时目录。

### 1.6 客户端接入以 TCP 为基础

客户端连接服务端使用 TCP 会话。

无论上层看起来是：

- 普通长连接；
- HTTP；
- WebSocket；
- 自定义控制协议；

底层控制连接统一基于 TCP。

客户端连接和植入物监听器是两条不同的网络平面：

- **客户端控制面**：客户端 ↔ 服务端；
- **植入物数据面**：植入物 ↔ 协议监听器。

两者不能混用密钥，不能混用端口职责，不能混用认证模型。

### 1.7 中间流量必须加密和混淆

客户端 ↔ 服务端、植入物 ↔ 服务端，两条链路都必须：

- 应用层加密；
- 完整性校验；
- 重放保护；
- 随机 padding；
- 流量外观处理；
- 协议级混淆。

```text

│ 服务端                                             │
│                                                    │
│  ┌────────────── 核心运行时 ──────────────┐        │
│  │ 启动器 / 文件存储 / 插件加载 / 审计     │        │
│  │ TCP 客户端入口 / 任务调度 / 调度变量     │        │
│  └──────────────────────────────────────┘        │
│                                                    │
│  ┌────────────── 服务端插件 ──────────────┐        │
│  │ 队列处理 / 结果处理 / 报告 / AI 工具    │        │
│  │ 清理 / 备份 / 扩展命令 / 扩展 API        │        │
│  └──────────────────────────────────────┘        │
│                                                    │
│  ┌────────────── 协议插件 ────────────────┐        │
│  │ UDP / TCP / HTTP / HTTPS / DNS（ICMP 延期）  │        │

└───────────────────────┬────────────────────────────┘

└────────────────────────────────────────────────────┘
```

服务端是能力中心，不是命令中心。

## 3. 服务端目录思想

服务端目录必须在启动目录下明确分家。

每个区域只做一类事情，避免“核心、插件、数据、运行时状态”混在一起。

推荐固定英文名称如下：

```text
<startup-directory>/
├── server_core/                 # 服务端主体代码
│   ├── bootstrap.py             # 启动入口
│   ├── runtime.py               # 服务端运行时全局对象
│   ├── file_store.py            # 文件数据库原子操作
│   ├── plugin_loader.py         # 插件加载、验证、注册
│   ├── task_queue.py            # 任务队列核心
│   ├── beacon_registry.py       # Beacon 身份与状态
│   ├── listener_manager.py      # 监听器生命周期调度
│   ├── payload_builder.py       # 载荷生成协调
│   ├── client_gateway.py        # TCP 客户端接入
│   ├── crypto_envelope.py       # 应用层加密与混淆
│   ├── policy.py                # 权限与风险策略
│   ├── audit.py                 # 审计事件
│   └── client_control_api.py    # TCP 客户端控制入口
│
├── implant_plugins/             # 下发给植入物的 Python 插件
│   ├── fs_list.py
│   ├── fs_read.py
│   ├── fs_write.py
│   ├── process_list.py
│   ├── network_info.py
│   ├── system_info.py
│   └── ...
│
├── server_plugins/              # 服务端本地执行的 Python 插件
│   ├── report_daily.py
│   ├── queue_cleaner.py
│   ├── result_archiver.py
│   ├── ai_tool_catalog.py
│   ├── webhook_notifier.py
│   └── ...
│
├── transport_plugins/           # 协议监听与载荷生成插件
│   ├── udp.py
│   ├── tcp.py
│   ├── http.py
│   ├── https.py
│   ├── dns.py
│   └── icmp.py              # v1 不实现，保留接口
│
├── data/                        # 文件数据库
│   ├── beacons/
│   ├── tasks/
│   ├── queues/
│   ├── results/
│   ├── listeners/
│   ├── payloads/
│   ├── plugins/
│   ├── clients/
│   ├── approvals/
│   ├── events/
│   └── keys/
│
├── runtime/                     # 可重建的运行时状态
│   ├── listeners/
│   ├── sessions/
│   ├── locks/
│   └── cache/
│
├── logs/                        # 运行日志与审计日志
│   ├── server.log
│   └── audit.jsonl
│
└── config/                      # 服务端配置
    ├── server.json
    ├── auth.json
    └── crypto.json
```

### 3.1 目录职责边界

| 目录 | 职责 | 是否可手工修改 |
|---|---|---|
| `server_core/` | 核心代码，必须保持小而稳 | 不直接改 |
| `implant_plugins/` | 下发给植入物的能力代码 | 可以新增/升级 |
| `server_plugins/` | 服务端本地的能力扩展 | 可以新增/升级 |
| `transport_plugins/` | 协议监听与载荷生成 | 可以新增/升级 |
| `data/` | 文件数据库，唯一持久化真相 | 不建议手改 |
| `runtime/` | 运行中临时状态，可重建 | 可清理 |
| `logs/` | 追加日志 | 可轮转，不手改正文 |
| `config/` | 配置 | 可编辑，需校验 |

### 3.2 主体文件不写业务命令

`server_core/` 里不应该出现：

```text
if command == "ls": ...
if command == "ps": ...
```

这些是插件职责。

`server_core/` 只负责：

- 找到插件；
- 验证插件；
- 执行插件；
- 记录结果；
- 维护状态；
- 提供运行时能力。

## 4. 服务端核心与插件的边界

### 4.1 必须保留在核心里的能力

以下能力不能轻易插件化，否则系统会失去可治理性：

1. 启动与工作目录锚定；
2. 文件数据库的原子读写原语；
3. 插件发现、加载与目录扫描；
4. 服务端运行时全局对象；
5. 任务队列和结果队列的基础状态机；
6. 策略、审批、权限判断；
7. 审计账本；
8. TCP 客户端接入；
9. 应用层加密与混淆基础能力；
10. 进程生命周期与优雅退出。

### 4.2 应该插件化的能力

以下能力默认做成插件：

- 每种协议监听器；
- 每种协议载荷生成；
- 任务结果格式化；
- 结果归档；
- 文件数据库清理；
- 报告生成；
- 通知；
- Webhook；
- AI 工具描述；
- 定时任务；
- 备份；
- 导入/导出；
- 指标采集；
- 自定义命令；
- 自定义管理 API；
- 数据转码；
- 插件版本迁移。

### 4.3 服务端也不要 Shell

服务端插件和管理操作不得默认依赖：

- `bash` / `sh` / `cmd` / `powershell`；
- `find` / `grep` / `awk` / `sed`；
- `curl` / `wget`；
- `netstat` / `ss` / `lsof`；
- 外部 Python 包管理命令。

推荐用：

- Python 文件 API；
- Python socket；
- Python asyncio；
- 标准库 JSON；
- 标准库 `pathlib`；
- 标准库 `hashlib` / `hmac`；
- 标准库 `ssl`；
- 自有协议插件；
- 自有任务处理插件。

如果某个能力确实必须使用外部命令，必须：

- 单独成插件；
- 不经过交互式 Shell；
- 使用参数数组；
- 有明确风险等级；
- 记录审计；
- 有失败回滚。

## 5. 文件数据库思想

### 5.1 文件数据库不是“随便存”

文件数据库的设计目标：

- 无外部数据库；
- 可读、可审计、可备份；
- 崩溃后可恢复；
- 能被服务端核心统一管理；
- 能被插件安全访问；
- 能在不重启服务端的情况下增量处理。

### 5.2 原子写入

任何持久化文件都应遵循：

```text
写临时文件
  → flush
  → fsync
  → 原子 rename
  → 目录 fsync
```

不允许直接在目标文件上覆盖写入半截内容。

### 5.3 单写者

每个状态目录应有明确的写者。

- 核心队列写者只允许一个；
- 插件不得直接竞争写同一文件；
- 插件需要通过运行时提供的存储 API 写入；
- 跨进程访问要加文件锁。

### 5.4 目录分片

不要把所有东西塞进一个巨大 JSON。

推荐按实体分目录：

```text
data/beacons/<beacon_id>/identity.json
data/tasks/<task_id>/task.json
data/tasks/<task_id>/code.enc
data/tasks/<task_id>/dispatch.json
data/results/<task_id>/result.json
data/results/<task_id>/output.bin
data/listeners/<listener_id>/listener.json
data/payloads/<payload_id>/payload.json
```

### 5.5 事件与索引

- 事实事件写入追加型 `events/YYYY-MM-DD.jsonl`；
- 索引文件是缓存，可以重建；
- 索引损坏不能导致真相丢失；
- 任务状态可以由事件和实体文件重建；
- 定期做一致性检查。

### 5.6 文件格式

每个持久化 JSON 文件至少包含：

- `format_version`
- `id`
- `created_at`
- `updated_at`
- `checksum`
- `status`
- 业务字段

二进制结果使用单独文件，与 `result.json` 通过 id/hash 关联。

### 5.7 文件数据库逻辑结构

#### Beacon

```text
data/beacons/<beacon_id>/
  identity.json       # Beacon 身份、公钥指纹、首次注册时间
  status.json         # 在线/离线/当前协议
  heartbeat.json      # 最后心跳、地址、协议
  routes.json         # 已知可用路径
```

#### Task

```text
data/tasks/<task_id>/
  task.json           # 任务元数据、状态、目标、插件引用
  code.enc            # 下发的加密代码或代码引用
  dispatch.json       # 下发轮次、监听器、协议、确认状态
```

#### Queue

```text
data/queues/<beacon_id>/
  pending.jsonl       # 待下发任务索引
  inflight.jsonl      # 已下发未确认任务
  completed.jsonl     # 已完成索引
```

#### Result

```text
data/results/<task_id>/
  result.json         # 状态、错误、hash、大小
  output.bin          # 完整输出，不截断
  chunks/             # 大结果分块元数据
```

#### Listener

```text
data/listeners/<listener_id>/
  listener.json       # 协议、地址、端口、插件版本、状态
  runtime.json        # 监听进程/线程状态，可从 file 重建
```

#### Payload

```text
data/payloads/<payload_id>/
  payload.json        # 监听器引用、投递方式、协议、公钥指纹
  code.enc            # 单阶段载荷代码或生成参数
```

#### Client session

```text
data/clients/<session_id>/
  session.json        # 客户端身份、权限、CSRF、过期时间
```

#### Plugin registry

```text
data/plugins/<plugin_id>/
  plugin.json         # 插件 manifest、hash、版本、类型
  history.jsonl       # 加载/卸载/失败记录
```

### 5.8 文件数据库的启动恢复

服务端启动时必须：

1. 确认工作目录；
2. 确保目录结构存在；
3. 扫描 `data/beacons`、`data/tasks`、`data/results`；
4. 清理写了一半的临时文件；
5. 重建索引；
6. 回收未确认的 inflight 任务；
7. 检查插件 manifest 与加载错误；
8. 检查监听器配置；
9. 恢复事件游标；
10. 启动 TCP 客户端入口。

## 6. 服务端运行时与插件执行

### 6.1 服务端运行时全局对象

服务端应维护一个全局运行时对象，向外暴露：

```text
server_runtime
  ├── config
  ├── workdir
  ├── file_store
  ├── plugin_registry
  ├── task_queue
  ├── result_store
  ├── beacon_registry
  ├── listener_manager
  ├── payload_builder
  ├── client_sessions
  ├── crypto
  ├── event_bus
  ├── command_registry
  ├── policy
  ├── audit
  ├── ai_tools
  └── metrics
```

### 6.2 双层执行模型

和植入物类似，服务端插件执行也采用：

```text
服务端全局运行时 G
  + 本次调用局部命名空间 L
```

- 插件普通变量写入 `L`；
- 插件可读、调用 `G`；
- 插件通过显式全局修改或运行时 API 修改 `G`；
- 插件可以注册新能力；
- 插件可以修改运行时调度参数；
- 插件可以替换部分处理器；
- 核心边界对象仍应受审计与权限约束。

### 6.3 服务端插件生命周期

```text
发现
  → 读取插件 manifest
  → 读取 manifest/hash/版本，加载失败打印错误
  → 检查能力声明
  → 加载到内存
  → 调用 init
  → 注册命令/路由/处理器/定时器
  → 进入运行
  → 支持 reload / disable / unload
```

### 6.4 服务端插件可以扩展什么

- 新 CLI 命令；
- 新 AI 工具；
- 新 API；
- 新结果处理器；
- 新队列策略；
- 新报告；
- 新通知；
- 新定时任务；
- 新加密/压缩算法；
- 新文件数据库迁移;
- 新协议监听器；
- 新载荷生成器；
- 新 Web 页面；
- 新审批规则插件。

### 6.5 服务端插件修改运行时

服务端插件可以通过运行时 API：

- 修改调度周期；
- 修改队列扫描间隔；
- 修改结果保留策略；
- 修改监听器默认参数；
- 注册新命令；
- 注册新协议；
- 替换载荷生成器；
- 改变客户端会话超时；
- 改变审计规则。

高风险修改必须：

- 有权限；
- 有审批；
- 有审计；
- 有旧值快照；
- 可回滚。

## 7. 协议插件与监听器思想

### 7.1 协议插件是服务端的工厂

每个协议插件同时具备两个身份：

1. **监听器工厂**：创建并运行该协议的监听器；
2. **载荷生成器**：根据监听器参数生成对应载荷。

两者必须来自同一个协议插件，版本一致，契约一致。

### 7.2 协议插件 manifest

每个协议插件是一个固定 Python 文件，包含：

- 协议 ID；
- 显示名称；
- 版本；
- 默认端口；
- 默认绑定地址；
- 传输能力；
- 最大包长；
- 是否需要分片；
- 是否支持服务端推送；
- 载荷生成函数；
- 监听器启动函数；
- 收包处理函数；
- 发包处理函数；
- 健康检查函数；
- 资源清理函数；
- 风险声明；
- 平台限制。

### 7.3 预设协议

首批核心协议：

```text
udp
tcp
http
https
dns
icmp  # v1 不实现，保留接口
```

后续扩展：

```text
websocket
tls
mtls
http2
doh
dot
quic
smb
named-pipe
```

### 7.4 监听器只管传输

监听器插件负责：

- 绑定地址/端口；
- 接收字节；
- 分片/重组；
- 重传/去重；
- 协议外观；
- 会话下发；
- 健康检查；
- 关闭。

它不负责：

- 任务业务；
- 结果语义；
- 插件语义；
- 策略审批；
- UI。

### 7.5 监听器与通用网关分层

```text
协议插件
  ↓ 字节流 / 数据报 / 请求响应
统一加密信封
  ↓
通用会话层
  ↓
任务队列 / 结果回收
```

这样新增协议不需要改任务层。

## 8. 监听器创建思想

### 8.1 服务端启动

服务端启动时可以指定客户端入口端口：

```text
python -m server_core.bootstrap --port 8080
```

默认行为：

```text
绑定 0.0.0.0:8080
工作目录 = 启动目录
加载 config/
初始化 data/
加载插件
启动 TCP 客户端入口
等待客户端连接
```

服务端启动后**不提供本地命令控制台，也不接受标准输入控制**。  
监听器创建、载荷生成、任务下发、插件管理和状态修改，全部必须通过客户端 TCP 控制面发起。

### 8.2 监听器创建由客户端发起

服务端起来后，客户端连接 TCP 控制面，通过控制请求调用监听器创建能力。

动作名使用英文，避免以后与中文显示名混杂：

```text
listener.create --protocol udp --host 0.0.0.0 --port 9000
listener.create --protocol tcp --host 0.0.0.0 --port 9001
listener.create --protocol http --host 0.0.0.0 --port 9002
listener.create --protocol https --host 0.0.0.0 --port 9003
listener.create --protocol dns --host 0.0.0.0 --port 5353
# v1 不实现 ICMP；保留接口
```

具体思想：

- 这些不是服务端本地 Shell 命令，而是客户端控制面的结构化动作；
- 动作处理器由服务端插件或核心注册；
- 创建监听器时调用对应 `transport_plugins/<protocol>.py`；
- 监听器获得独立 ID；
- 配置写入 `data/listeners/<listener_id>/listener.json`；
- 运行时状态写入 `runtime/listeners/`；
- 结果返回给发起请求的客户端；
- 服务端自身不读取键盘输入，不维护本地交互式命令行。

### 8.3 监听器参数

至少包括：

- 协议；
- 绑定地址；
- 绑定端口；
- 公网地址/公网域名；
- 是否启用混淆；
- 加密套件；
- 载荷模板；
- 回连参数；
- 风险等级；
- 允许的客户端类型；
- 备注。

### 8.4 监听器生命周期

```text
created
  → starting
  → listening
  → degraded
  → stopped
  → failed
```

状态写入文件；服务端重启时可根据 `data/listeners` 恢复。

### 8.5 监听器停止

必须是插件提供的 `stop` 能力，不使用 Shell 的 `kill`。

停止过程：

1. 标记停止；
2. 拒绝新会话；
3. 等待已有会话安全结束；
4. 关闭 socket；
5. 写入监听器状态；
6. 记录审计事件。

## 9. 载荷生成思想

### 9.1 监听器生成之后生成载荷

载荷不是凭空生成的，而是绑定某个监听器。

载荷生成输入：

- 监听器 ID；
- 协议；
- 公网地址；
- 端口；
- 加密公钥/指纹；
- 回连参数；
- 插件集合；
- 投递方式；
- 客户端平台；
- 混淆/伪装策略。

### 9.2 载荷是单阶段的

无论输出是：

```text
echo "<python>" | python
```

还是：

```text
curl "<url>" | python
```

本质都是：

```text
一段 Python 代码 → exec 执行
```

不存在双阶段状态机。

### 9.3 载荷生成插件化

协议插件负责：

- 根据自己的协议生成载荷骨架；
- 把监听器地址/端口写入载荷；
- 选择协议编解码；
- 生成协议特定外观；
- 返回可投递载荷。

服务端只负责：

- 选择协议插件；
- 传入监听器配置；
- 记录载荷 ID；
- 存储载荷元数据；
- 生成下载入口或 echo/curl 命令。

### 9.4 载荷生成命令

```text
payload.generate --listener <listener_id> --method echo
payload.generate --listener <listener_id> --method curl
payload.generate --listener <listener_id> --method short
payload.list
payload.show <payload_id>
payload.delete <payload_id>
```

### 9.5 载荷协议策略

载荷生成时不仅绑定一个监听器，还可以绑定协议选择策略。

策略类型：

- `fixed`：只使用某个协议；
- `fallback`：主协议失败后回退到备用协议；
- `random`：从候选协议中随机选择；
- `weighted-random`：按权重随机选择。

示例：

```text
HTTPS 为主，DNS 为备用
```

或：

```text
[HTTPS, DNS] 每轮随机选择一个
```

策略写入载荷元数据和植入物全局运行时，允许后续通过服务端下发的 Python 控制代码修改。

### 9.6 协议升级载荷

服务端应能生成“协议升级任务”：

```text
现有 TCP 植入物
  → 服务端创建 HTTPS 监听器
  → 服务端生成一段 Python 升级代码
  → 通过现有 TCP 通道下发
  → 植入物在内存中加载 HTTPS 协议插件
  → 探测 HTTPS 监听器
  → 验证成功
  → 切换主协议
  → 旧 TCP 保留为备用或关闭
```

升级计划必须绑定：

- 旧监听器；
- 新监听器；
- 新协议；
- 回退策略；
- 验证步骤；
- 失败回滚；
- 审计记录。

### 9.7 载荷存储

```text
data/payloads/<payload_id>/
  payload.json       # 元数据、监听器引用、协议、公钥指纹
  code.enc           # 单阶段载荷代码或生成参数
```

载荷生成后：

- 可下载；
- 可复制 echo 命令；
- 可复制 curl 命令；
- 可生成短 Python 下载器；
- 记录下载次数和审计事件。

## 10. 客户端 TCP 接入思想

### 10.1 两种监听器

服务端有两类监听器：

1. **客户端入口**
   - 固定核心能力；
   - 客户端 ↔ 服务端；
   - TCP 基础；
   - 端口由启动参数指定；
   - 默认 `0.0.0.0:<port>`；
   - 认证、会话、审计、控制面。

2. **植入物协议监听器**
   - 插件能力；
   - 植入物 ↔ 服务端；
   - 协议由 `transport_plugins` 决定；
   - 每个监听器独立 ID；
   - 端口和协议可配置。

### 10.2 客户端连接流程

```text
客户端建立 TCP
  → 协商加密
  → 验证客户端身份
  → 创建会话
  → 进入控制面
  → 请求 API / 事件流 / 任务
```

### 10.3 客户端控制面能力

- 登录与授权；
- Beacon 列表；
- 任务创建；
- 任务查询；
- 结果查看；
- 监听器管理；
- 载荷生成；
- 插件管理；
- 审批；
- 审计；
- AI 工具；
- 事件订阅。

### 10.4 TCP 是基础，不是全部

上层可以是：

- 自己的 TCP 控制协议；
- HTTP over TCP；
- WebSocket over TCP；
- 未来可替换的客户端协议插件。

但无论上层是什么，客户端和服务端的会话必须：

- 使用同一套身份认证；
- 使用同一套加密信封；
- 使用同一套审计；
- 不能各自维护一套权限。

## 11. 加密与混淆

### 11.1 两类密钥域

必须区分：

- **客户端控制面密钥域**：客户端 ↔ 服务端；
- **植入物数据面密钥域**：植入物 ↔ 监听器。

两类密钥不能复用。

### 11.2 应用层加密

无论底层是否使用 TLS：

- 任务、结果、插件代码、控制命令都要应用层加密；
- 完整性校验；
- 重放保护；
- 消息序号；
- 会话 nonce。

### 11.3 混淆

- 随机 padding；
- 长度掩盖；
- 随机分片；
- 时间抖动；
- HTTP/DNS 协议外观适配；ICMP v1 不实现。
- 心跳/背景流量；
- 客户端与植入物分别使用不同流量策略。

### 11.4 密钥与轮换

- 服务端主密钥；
- 会话密钥；
- 监听器密钥；
- Beacon 密钥；
- 载荷绑定密钥；
- 插件配置密钥（v1 不做签名）；
- 全局运行时暴露密钥管理器；
- 控制插件可以触发轮换；
- 旧密钥保留过渡窗口。

## 12. 文件队列与任务流

### 12.1 任务生成

任务由客户端、AI 或服务端插件生成。

任务写入：

```text
data/tasks/<task_id>/task.json
data/queues/<beacon_id>/pending.jsonl
```

### 12.2 植入物拉取

植入物连接监听器：

1. 认证 Beacon；
2. 上报结果；
3. 请求任务；
4. 服务端读取该 Beacon 队列；
5. 返回全部可下发任务；
6. 植入物关闭连接；
7. 服务端标记已下发但未确认。

### 12.3 结果回收

植入物下一轮连接：

1. 上传结果；
2. 服务端验证任务 ID；
3. 写入 `data/results/<task_id>/`；
4. 确认；
5. 更新任务状态；
6. 写事件；
7. 通知客户端。

### 12.4 队列的不可变原则

- 任务一旦创建，ID 不可变；
- 下发记录追加，不覆盖；
- 结果一旦写入，不静默修改；
- 需要修正时写新事件，而不是覆盖历史；
- 旧结果可以归档，但不能无声消失。

## 13. Beacon 身份与状态

### 13.1 Beacon 身份

Beacon ID 在首次注册时生成，持久化：

```text
data/beacons/<beacon_id>/identity.json
```

身份包含：

- Beacon ID；
- 公钥指纹；
- 首次注册时间；
- 平台信息；
- 初始监听器协议；
- 初始协议策略；
- 允许的插件能力。

### 13.2 Beacon 状态

```text
未注册
 → 已注册
 → 在线
 → 降级
 → 失联
 → 恢复
```

状态写入文件，内存只是缓存。

### 13.3 协议切换不能改变身份

Beacon 从 UDP 切换到 HTTPS 后：

- Beacon ID 不变；
- 任务历史不变；
- 结果归属不变；
- 队列不变；
- 仅 `routes.json` / `status.json` 更新。

## 14. 服务端运行期不提供本地控制输入

### 14.1 设计思想

服务端启动后只提供服务，不提供交互式命令控制台。

不允许通过以下方式控制系统：

- 服务端本地标准输入；
- 本地 Shell 命令；
- 本地管理脚本直接修改运行状态；
- 本地文件手工修改后热加载；
- 仅限本机的 Unix Socket 管理后门；
- 任何绕过客户端认证的控制入口。

所有控制都必须经过：

```text
客户端 → TCP 控制连接 → 认证 → 策略 → 服务端能力
```

### 14.2 谁可以控制

两类客户端：

1. **人类 Web 客户端**
   - 有可视化界面；
   - 管理监听器、载荷、Beacon、任务、插件、审批；
   - 命令输入支持补全和历史。

2. **AI 一次性客户端**
   - 以 `client_ai.py` 形式存在；
   - 通过 TCP 调用服务端能力；
   - 适合脚本化、一次性请求和自动化；
   - 使用同一认证、策略和审计。

### 14.3 控制动作

监听器创建、载荷生成、任务下发、插件管理、策略修改、审批、结果查看等动作，统一是客户端控制面动作。

动作名可以保持英文：

```text
listener.create
listener.list
listener.show
listener.stop
payload.generate
payload.list
beacon.list
task.create
task.list
task.cancel
result.list
plugin.list
plugin.reload
audit.tail
```

但服务端不提供输入这些命令的本地终端。

### 14.4 服务端启动参数不是运行控制

启动参数只用于：

- 指定客户端 TCP 端口；
- 指定配置文件路径；
- 指定工作目录；
- 指定日志级别。

启动后不再接受控制型标准输入。

### 14.5 审计

每个客户端控制动作记录：

- 客户端身份；
- 会话 ID；
- 来源地址；
- 动作名；
- 参数；
- 结果；
- 是否修改持久状态；
- 关联监听器/Beacon/任务。

## 15. 服务端插件与服务端运行时变量

### 15.1 插件可以读写的对象

服务端插件可以读写：

- 监听器管理器；
- 任务队列；
- 结果存储；
- Beacon 注册表；
- 客户端会话；
- 插件注册表；
- 事件总线；
- 命令注册表；
- AI 工具注册表；
- 加密配置；
- 调度参数；
- 监听器参数；
- 回连策略。

### 15.2 插件扩展方式

插件可注册：

```text
command
api_route
event_handler
task_processor
result_processor
scheduled_job
listener_protocol
payload_generator
crypto_suite
report
ai_tool
web_view
```

### 15.3 插件不能做的事

- 绕过审计；
- 绕过审批；
- 直接修改其他插件源码；
- 读写未授权密钥；
- 启动 Shell；
- 把插件代码随意落盘到工作目录之外；
- 静默删除审计日志；
- 绕过客户端认证。

### 15.4 插件热重载

服务端插件应支持：

- 加载；
- 卸载；
- 重新加载；
- 禁用；
- 回滚到旧版本。

热重载不能：

- 丢失正在进行的任务；
- 破坏进行中的结果回收；
- 改变 Beacon 身份；
- 让监听器端口泄漏。

## 16. 客户端、Web 与 AI

### 16.1 客户端控制面

客户端通过 TCP 与服务端建立控制会话，获得：

- Beacon 状态；
- 任务流；
- 结果流；
- 事件流；
- 审批流；
- 插件/协议/监听器列表。

### 16.2 Web

Web 是服务端控制面的可视化驾驶舱：

- 服务端状态；
- 监听器管理；
- 协议路径；
- 任务队列；
- 结果；
- 插件；
- 载荷；
- 审批；
- 审计；
- AI 计划。

### 16.3 AI

AI 通过服务端工具目录调用能力：

- 不能直接连接植入物；
- 不能绕过 TCP 控制面；
- 不能直接读取密钥；
- 不能绕过审批；
- 不能修改服务端核心；
- 可以使用服务端插件注册的工具。

### 16.4 客户端与服务端流量

客户端 ↔ 服务端流量：

- TCP 基础；
- 应用层加密；
- 混淆；
- 会话认证；
- 重放保护；
- 权限校验；
- 审计。

---

## 17. 服务端安全边界

### 17.1 信任边界

- 服务端核心受信；
- 服务端插件分级受信；
- 客户端受认证；
- AI 受策略约束；
- 植入物受身份验证；
- 目标输出不可信；
- 传输不可信。

### 17.2 文件权限

- 密钥文件最小权限；
- 插件文件只读；
- 数据目录仅服务端可写；
- 客户端只通过 API 操作，不直接读写数据目录；
- 审计日志不可由客户端删除。

### 17.3 插件签名

- v1 不做签名/信任机制；
- 插件目录即信任边界；
- 启动和热重载时只要文件存在就尝试加载；
- 加载失败打印错误并保留旧插件继续运行；
- 后续可扩展 Ed25519 签名。

### 17.4 加密

- 客户端控制面加密；
- 植入物数据面加密；
- 插件代码加密；
- 载荷加密；
- 密钥域隔离；
- 轮换；
- 旧密钥过渡。

---

## 18. 失败与恢复

### 18.1 服务端重启

- 从启动目录恢复；
- 扫描文件数据库；
- 清理临时文件；
- 重建索引；
- 恢复监听器配置；
- 恢复未确认队列；
- 继续运行。

### 18.2 插件失败

- 单次插件调用异常被捕获；
- 插件失败不拖垮核心；
- 记录插件名、版本、错误；
- 可禁用/回滚插件；
- 不影响已经持久化的任务和结果。

### 18.3 监听器失败

- 标记 `failed`；
- 记录事件；
- 可重建监听器；
- 不影响其他监听器；
- 不丢任务队列；
- 载荷仍保留。

### 18.4 客户端断开

- 会话标记断开；
- 不影响任务；
- 客户端重新连接后恢复状态；
- 事件流可补发；
- 会话过期后清理。

### 18.5 文件损坏

- 每个文件带 checksum；
- 索引可重建；
- 事件日志可恢复；
- 损坏文件隔离到 `data/quarantine/`；
- 不覆盖真相，不静默丢弃。

---

## 18.6 Python 代码下发出口统一剥离注释

服务端必须有一个统一的代码下发出口：

```text
所有插件 / raw 脚本 / 控制代码 / 载荷代码
  → CodeDeliveryPipeline
  → tokenize 去注释
  → compile 校验
  → 加密
  → 发送
```

强制规则：

- 任何下发路径不得绕过；
- 不得只在某个插件内部临时处理；
- 客户端上传的 `.py` 同样必须剥离；
- raw `python.exec` 同样必须剥离；
- 单阶段载荷中的执行代码同样必须剥离；
- 原始源码可保留在服务端供维护；
- 下发版本只保留剥离注释后的代码；
- 剥离失败时拒绝下发并记录错误。

## 19. 插件目录与固定 Python 形式

### 19.1 一个插件一个 Python 文件

为了保持目录清楚、部署简单和“文件即数据库”的哲学，建议：

```text
implant_plugins/fs_list.py
implant_plugins/fs_read.py
server_plugins/report_daily.py
transport_plugins/udp.py
```

每个文件内包含：

- `PLUGIN` 元数据；
- `init` 函数；
- 主处理函数；
- 清理函数；
- 能力声明。

### 19.2 插件文件不落盘复制

插件代码在服务端：

- 从插件目录读取；
- 加载到内存；
- 记录插件加载错误；
- 执行。

发送给植入物时：

- 加密；
- 不写入目标磁盘；
- 目标端只在内存执行。

### 19.3 插件与文件数据库的关系

- 插件源码在插件目录；
- 插件运行结果在 `data/`；
- 插件索引在 `data/plugins`；
- 插件临时状态在 `runtime/`；
- 插件日志在 `logs/`。

## 20. 总体工作流

```text
服务端启动
  → 锚定启动目录
  → 初始化 data/ 文件数据库
  → 加载 server_core
  → 加载 server_plugins
  → 加载 transport_plugins
  → 启动 TCP 客户端入口（默认 0.0.0.0:<port>）
  → 等待客户端连接
  → 客户端完成认证
  → 客户端创建协议监听器
  → 生成单阶段载荷
  → 客户端下发任务到队列
  → 植入物连接协议监听器
  → 植入物拉取 Python 代码
  → 植入物并行执行
  → 植入物回传结果
  → 结果写入文件数据库
  → 客户端查看任务和完整结果
```

---

## 21. 默认决策

1. 服务端工作目录 = 启动目录。
2. 不依赖外部数据库，所有持久化使用文件。
3. 服务端核心保持小而稳，其余能力插件化。
4. 服务端也执行 Python 插件，并允许修改运行时全局变量。
5. 服务端插件可扩展命令、API、任务处理、结果处理、AI 工具等能力。
6. 客户端 ↔ 服务端使用 TCP 基础连接。
7. 客户端入口默认 `0.0.0.0:<启动参数端口>`。
8. 植入物监听器由协议插件创建，端口和协议可配置。
9. 协议插件的生成与监听必须成对存在。
10. v1 首批协议：UDP、TCP、HTTP、HTTPS、DNS；ICMP 暂不实现。
11. 所有客户端和植入物流量都必须应用层加密和混淆。
12. 服务端命令不通过 Shell 执行。
13. 插件固定为 Python 文件。
14. 插件源码、运行状态、持久数据、日志严格分目录。
15. 文件数据库必须原子写、可恢复、可审计。
16. 载荷始终为单阶段 Python 代码，交付方式可以是 echo、curl 或短下载器。
17. 服务端启动后不提供本地命令控制台，不接受标准输入控制。
18. 监听器、载荷、任务和插件管理全部通过客户端 TCP 控制面下发。
19. 人类 Web 与 AI 一次性客户端使用同一控制面、同一策略和同一审计。
20. 载荷生成时绑定起始协议和协议策略，植入物不硬编码默认协议。
21. 协议策略支持 fixed、fallback、random、weighted-random。
22. 协议升级通过服务端下发的 Python 升级任务完成，失败自动回滚。
23. 所有插件和运行时修改必须有版本、权限和审计。

## 22. 设计验收问题

每个服务端设计决策都应回答：

1. 它是否保持在启动目录以内？
2. 它是否把持久化数据写成了可恢复的文件？
3. 它是否避免了外部数据库依赖？
4. 它是否避免了不必要的 Shell/PowerShell？
5. 它是否把能力做成了插件，而不是写死在核心？
6. 它是否允许服务端插件修改运行时变量？
7. 它是否允许插件扩展命令、任务、结果、AI 或 API？
8. 协议监听器是否由插件创建？
9. 协议载荷是否由同一协议插件生成？
10. 客户端入口是否基于 TCP 且默认绑定 `0.0.0.0:<port>`？
11. 客户端控制面和植入物数据面是否密钥隔离？
12. 所有流量是否都加密和混淆？
13. 文件数据库是否原子写、可重建、可审计？
14. 服务端重启后是否能从文件恢复？
15. 监听器失败是否不会影响其他监听器？
16. 插件失败是否不会拖垮核心？
17. 任务与结果是否有唯一 ID 和完整生命周期？
18. 插件目录、数据目录、日志目录是否严格分开？
19. 人类和 AI 是否使用同一控制面和审批？
20. 服务端启动后是否没有任何本地控制输入入口？
21. 是否真的做到了“核心极简、插件扩展、文件持久、TCP 接入、多协议监听”？

## 23. 最终总结

服务端的思想不是“写很多接口”。

服务端只做四件事：

1. **组织任务**；
2. **提供代码**；
3. **接收结果**；
4. **管理能力与路径**。

其余全部通过插件扩展：

- 协议插件负责监听和载荷生成；
- 服务端插件负责运维、处理、报告、AI 和扩展功能；
- 植入物插件负责目标端能力；
- 文件数据库负责持久化；
- TCP 控制面负责人与 AI 的接入。

最终设计灵魂是：

> **核心极简，插件扩展；文件持久，不靠数据库；无必要不 Shell；启动目录即世界；TCP 接入，多协议监听；运行时可变，插件可增；v1 插件目录即信任，所有动作有版本与审计。**

这份文档作为服务端方向的总体思想基线。  
下一步应基于它拆出“服务端核心运行时”“文件数据库”“协议监听插件”“载荷生成”“TCP 客户端控制面”五个详细设计篇。

## 24. v1 最终执行参数补充

- 插件签名：不做；插件目录即信任边界。
- 插件热重载：客户端可编辑服务端插件，保存后立即热重载；加载失败保留旧版本并显示错误。
- 审批模式：
  - 逐条审批：全部动作拦截，人工逐条放行；
  - 全部放行：只记录审计，不拦截。
- 协议升级：显式任务触发，无人工审批。
- SOCKS5：
  - 端口 1080；
  - 绑定 0.0.0.0；
  - 用户名/密码；
  - 来源 IP 白名单；
  - 允许多隧道；
  - 断开不自动重建。
- 文件：
  - 上传/下载最大 1 GB；
  - 分块 1 MB；
  - 支持断点续传；
  - 覆盖必须显式确认；
  - 结果与 Artifact 永久保留。
