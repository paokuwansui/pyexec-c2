## 0. 一句话定义

**插件是系统唯一的业务能力单元。**

- 植入插件：在目标端内存中执行，负责文件、进程、网络、代理、上传、下载、截图、脚本执行等能力。
- 服务端插件：在服务端执行，负责协议监听、载荷生成、结果处理、代理网关、文件服务、AI 工具、报告、清理、备份等扩展能力。
- 插件代码永远是 Python。
- 插件不是 Shell 命令的包装。
- 插件不是固定命令表的别名。
- 插件是可版本化、可审计、可独立升级的能力胶囊；v1 不做签名校验。

## 1. 插件体系第一原则

### 1.1 能解耦的全部插件化

必须保留在核心中的：

- 插件加载与目录扫描；
- 插件运行时；
- 任务/结果基础状态机；
- 通信；加密；审计；
- 权限与策略；
- 执行器。

应该插件化的：

- 所有业务命令；
- 所有平台命令实现；
- 所有文件传输能力；
- 所有代理能力；
- 所有协议监听与载荷生成；
- 所有结果处理；
- 所有扩展页面能力；
- 所有 AI 工具；
- 所有报告、通知、清理、备份。

### 1.2 插件不依赖 Shell

插件默认使用 Python 原生能力实现：

| 能力 | 默认实现 |
|---|---|
| 列目录 | Python 文件系统 API |
| 读文件 | Python 文件系统 API |
| 进程列表 | Python 系统接口 |
| 网络连接 | Python 系统接口 |
| 上传/下载 | Python 分块读写 |
| 代理 | Python socket |
| 文件编辑 | Python 文件 API |
| 截图 | Python 系统接口 |
| 系统信息 | Python 平台接口 |

禁止：

- `sh -c`；
- `cmd /c`；
- `powershell -Command`；
- 通过 Shell 管道拼接命令；
- 依赖目标机存在 `ls`、`cat`、`ps`、`netstat` 等命令。

### 1.3 平台不同则拆命令

同一个逻辑能力，如果在 Linux 和 Windows 上的实现方式不同，必须拆成两个插件、两个命令。

命名规则：

- Linux 命令：`l` 前缀；
- Windows 命令：`w` 前缀；
- 跨平台且 Python 代码真正相同的：保持统一命令名，不加前缀。

例如：

```text
Linux 进程列表   → lps
Windows 进程列表 → wps
```

不能继续使用一个模糊的 `ps` 命令，让插件内部再判断平台。

### 1.4 插件是能力，不是一段脚本

插件不是“发过去就执行”的裸代码。

插件包含：

- 身份；
- 版本；
- 平台声明；
- 能力声明；
- 输入 schema；
- 输出 schema；
- 风险等级；
- 是否写盘；
- 是否联网；
- 是否长任务；
- 是否流式；
- 是否可并发；
- 版本与 hash（v1 不做签名）；
- 代码本体。

### 1.5 全部能力都要可被 UI 发现

Web 客户端必须能：

- 查看插件目录；
- 按平台筛选；
- 按类型筛选；
- 按风险筛选；
- 搜索命令；
- 查看说明；
- 查看参数；
- 查看历史执行；
- 直接执行；
- 查看源码；
- 启用/禁用。

### 1.6 结果不截断

插件结果：

- 完整存储；
- 完整返回；
- Web 可滚动查看；
- 大结果可分段加载；
- 正则提取只影响视图，不修改原始结果。

## 2. 插件分层

```text
┌──────────────────────────────────────────────┐
│ 客户端插件/能力呈现层                         │
│ 命令补全 / 正则提取 / 文件编辑器 / 目录视图    │
├──────────────────────────────────────────────┤
│ 服务端插件层                                 │
│ 协议监听 / 载荷生成 / 代理网关 / 结果处理      │
│ 文件服务 / AI 工具 / 报告 / 清理 / 备份        │
├──────────────────────────────────────────────┤
│ 植入插件层                                   │
│ 文件 / 进程 / 网络 / 代理 / 上传下载 / 截图    │
│ 脚本执行 / 系统信息 / 平台专用能力             │
└──────────────────────────────────────────────┘
```

三类插件不是孤立的：

- 一个代理功能通常由“植入代理插件 + 服务端代理网关 + Web 隧道视图”共同完成；
- 一个下载功能通常由“植入文件读取插件 + 服务端 artifact 服务 + Web 下载按钮”共同完成；
- 一个文件编辑功能通常由“Web 编辑器 + 服务端任务 + 植入 fs.write 插件”共同完成。

### 3.1 目录职责

| 目录 | 职责 |
|---|---|
| `implant_plugins/common/` | 真正跨平台的 Python 插件 |
| `implant_plugins/linux/` | Linux 专用插件，命令必须带 `l` 前缀 |
| `implant_plugins/windows/` | Windows 专用插件，命令必须带 `w` 前缀 |
| `server_plugins/` | 服务端侧插件 |
| `transport_plugins/` | 协议监听与载荷生成插件 |
| `data/` | 插件版本、任务、结果、artifact 等文件数据库 |

### 3.2 平台前缀规则

- 同一能力，如果 Linux 和 Windows 实现不同：
  - Linux 插件命令：`l` + 基础名；
  - Windows 插件命令：`w` + 基础名。
- 如果同一份 Python 代码可以在两个平台正常运行，可以保留统一命令名。
- 平台专用插件不得伪装成跨平台插件。
- 服务端必须拒绝把 Linux 插件下发给 Windows Beacon，反之亦然。

## 4. 植入插件体系

### 4.1 插件分类

参照 Cobalt Strike 常见操作能力，结合本系统“无 Shell、内存执行、Python 原生”的原则，植入插件分为：

#### 文件类

- `fs.list`：目录浏览；
- `fs.read`：读取文件；
- `fs.write`：写文件、保存编辑结果；
- `fs.stat`：文件信息；
- `fs.mkdir`：创建目录；
- `fs.remove`：删除文件/目录；
- `fs.move`：移动/重命名；
- `fs.copy`：复制；
- `fs.upload`：从服务端接收文件并写到目标路径；
- `fs.download`：从目标读取文件并上传到服务端；
- `fs.chmod` / `fs.acl`：权限相关，按平台拆分；
- `fs.search`：文件搜索。

#### 进程类

- `lps`：Linux 进程列表；
- `wps`：Windows 进程列表；
- `lkill` / `wkill`：终止进程；
- `lsuspend` / `wsuspend`：挂起进程；
- `lresume` / `wresume`：恢复进程。

#### 网络类

- `lnetstat`：Linux 连接与监听；
- `wnetstat`：Windows 连接与监听；
- `lnetinfo`：Linux 网络接口；
- `wnetinfo`：Windows 网络接口；
- `lnetdns` / `wnetdns`：DNS 缓存/配置；
- `lnetroute` / `wnetroute`：路由表。

#### 系统类

- `system.info`：跨平台基础信息；
- `lenv` / `wenv`：环境变量；
- `lusers` / `wusers`：用户列表；
- `lservices` / `wservices`：服务列表；
- `wregistry`：Windows 注册表；
- `lscreenshot` / `wscreenshot`：屏幕截图；
- `lclipboard` / `wclipboard`：剪贴板；
- `ldrives` / `wdrives`：磁盘列表。

#### 代理与隧道类

- `proxy.socks5`：植入物本地 SOCKS5 入口；
- `proxy.tcp`：TCP 转发；
- `proxy.portfwd`：端口转发；
- `proxy.http`：HTTP 代理；
- `proxy.reverse`：反向代理。

代理插件应尽量做成跨平台 Python 实现；如果底层 socket 行为需要按平台区分，则拆分到 `lproxy` / `wproxy`。

#### 执行与脚本类

- `python.exec`：执行服务端下发的 Python 代码；
- `python.exec_file`：执行客户端选择的本地 `.py` 文件；
- `python.validate`：校验 Python 代码语法；
- `python.expression`：执行单表达式并返回结构化结果。

这里不是 Shell，也不是外部 Python 解释器，而是在植入物执行内核中 `exec`。

#### 高风险类

- 持久化；
- 凭据读取；
- 令牌操作；
- 浏览器数据；
- 高权限系统配置修改。

这些必须：

- 独立插件；
- R4 风险；
- v1 默认放行，保留审批接口；
- 默认不预装；
- 只允许授权范围内使用。

### 4.2 参照旧代码的迁移映射

旧代码中已有的类型：

```text
sysinfo
pwd
ls
cat
exec
shell
fs.list
fs.read
ps.list
net.info
```

新插件体系建议：

| 旧能力 | 新插件 |
|---|---|
| sysinfo | `system.info` |
| pwd | `fs.pwd` |
| ls | `fs.list` |
| cat | `fs.read` |
| ps.list | 拆为 `lps` / `wps` |
| net.info | 拆为 `lnetstat` / `wnetstat`，另保留跨平台基础 `net.info` |
| fs.list | `fs.list` |
| fs.read | `fs.read` |
| exec | 移除，改为 `python.exec` |
| shell | 移除，默认不提供 Shell |

### 4.3 旧代码优化原则

1. 不再用统一 `ps` 命令内部判断平台；
2. 不再把 Shell 当作默认能力；
3. 不再返回非结构化的大段字符串作为唯一结果；
4. 不在插件之间共享可写全局命名空间；
5. 每个平台插件只做自己的实现；
6. 输出包含 `ok`、`data`、`lines`、`error`、`meta`；
7. 长任务必须可查询、可取消；
8. 大输出必须支持分块；
9. 文件传输必须支持 checksum 和断点续传思想；
10. 插件必须通过 manifest 声明能力与风险。

### 4.4 插件输出结构

建议统一为：

```text
{
  ok: bool,
  command: string,
  target: string,
  data: object,
  lines: [string],
  error: string|null,
  meta: {
    platform,
    started_at,
    finished_at,
    bytes,
    truncated: false,
    task_id
  }
}
```

`lines` 用于人类阅读，`data` 用于程序/AI 处理。  
`truncated` 只有在显式声明的不完整结果时才为 true。

## 5. 代理插件思想

### 5.1 组成

代理能力由三部分组成：

1. 植入物代理插件；
2. 服务端代理网关插件；
3. 客户端隧道管理界面。

### 5.2 工作方式

```text
客户端创建隧道
  → 服务端生成代理任务
  → 植入物启动 proxy.socks5 / proxy.tcp 插件
  → 客户端通过服务端代理网关连接
  → 服务端把字节流封装成 C2 消息
  → 植入物代理插件转发到目标
  → 响应沿原路返回
```

### 5.3 代理能力

- SOCKS5；
- TCP 转发；
- 端口转发；
- HTTP 代理；
- 反向代理。

### 5.4 代理规则

- 代理流量必须加密；
- 代理流量必须可审计；
- 每个代理会话有 ID；
- 支持空闲超时；
- 支持最大并发；
- 支持 ACL；
- 支持停止隧道；
- 不用 Shell 调用系统代理工具。

### 5.5 Web 视图

- 隧道列表；
- 目标 Beacon；
- 类型；
- 本地入口；
- 远端目标；
- 状态；
- 流量统计；
- 开始/停止；
- 错误原因。

## 6. 下载与上传插件思想

### 6.1 下载

```text
目标文件
  → 植入物 fs.download 插件读取
  → 分块加密回传
  → 服务端 artifact 服务拼装
  → 客户端下载
```

要求：

- 不截断；
- 计算文件 hash；
- 支持断点续传；
- 支持大文件；
- 记录文件路径、大小、权限、mtime；
- 目标端不生成额外临时文件。

### 6.2 上传

```text
客户端选择本地文件
  → 服务端接收为 artifact
  → 任务分块下发给植入物
  → 植入物 fs.upload 插件写入目标路径
  → 校验 hash
  → 返回结果
```

要求：

- 用户明确指定目标路径；
- 写盘属于显式文件操作，不违反“无必要不落盘”；
- 默认不覆盖，需显式 overwrite；
- 支持断点续传；
- 支持失败清理；
- 不通过 Shell 的 `cat > file`。

### 6.3 文件编辑

Web 文件浏览器支持打开文件：

```text
点击文件
  → 编辑器打开
  → 显示完整内容
  → 编辑
  → 保存
  → 服务端生成 fs.write 任务
  → 植入物原子写回
  → 返回新 hash/mtime
```

要求：

- 文本编辑器只对文本文件开放；
- 二进制文件提供下载/hex 查看，不直接文本编辑；
- 保存前比较远端文件 hash，避免覆盖并发修改；
- 保存失败要明确报错；
- 支持编码选择；
- 支持查看完整文件；
- 文件写回属于用户明确文件操作。

### 6.4 Web 目录浏览

文件浏览器应提供：

- 当前路径；
- 面包屑；
- 上一级；
- 刷新；
- 目录/文件区分；
- 文件大小；
- 权限；
- 修改时间；
- 排序；
- 搜索；
- 双击进入目录；
- 点击文件预览/编辑；
- 下载；
- 上传；
- 新建目录；
- 删除；
- 重命名。

目录浏览插件：

- Linux 可用 `lfs.list`；
- Windows 可用 `wfs.list`；
- 如果 `fs.list` 的 Python 实现跨平台一致，则保留统一 `fs.list`。

## 7. 下发本地 Python 文件思想

### 7.1 场景

操作员在 Web 上点击：

```text
执行本地 Python
  → 选择本地 .py 文件
  → 服务端读取并计算 hash
  → 作为任务代码发送到目标
  → 植入物在内存中 exec
  → 返回完整结果
```

### 7.2 插件

可使用：

- `python.exec_file`：跨平台、执行完整 Python 文件内容；
- `python.exec`：执行短 Python 代码片段；
- `python.validate`：只校验语法。

### 7.3 安全规则

- 不写目标磁盘；
- 不在目标端生成 `.py`；
- 不经过 Shell；
- 必须展示文件 hash；
- 高风险代码在 v1 默认放行，但保留审批接口与审计；
- 输出完整返回；
- 文件过大时使用分块上传和分块下发；
- 插件代码与用户脚本在同一任务作用域中运行，但运行时对象可见、可调用、可按规则修改。

### 7.4 Web 展示

- 文件名；
- 大小；
- hash；
- 目标 Beacon；
- 执行按钮；
- 危险提示；
- 完整输出；
- 历史记录。

## 8. 服务端插件体系

### 8.1 服务端插件类型

#### 协议插件

- 监听器创建；
- 收包/发包；
- 分片/重组；
- 协议外观；
- 载荷生成。

#### 代理网关插件

- 接收客户端代理连接；
- 与植入物代理插件对接；
- 管理隧道；
- 流控；
- 审计。

#### Artifact 服务插件

- 文件上传接收；
- 大文件拼装；
- 下载分块；
- hash 校验；
- 文件元数据。

#### 结果处理器插件

- 文件结果格式化；
- 图片结果转 artifact；
- 网络拓扑增量更新；
- 结构化结果转表。

#### 正则过滤器插件

- 保存命名正则规则；
- 对结果做服务端侧提取；
- 不修改原始结果；
- 为 Web 和历史提供可复用过滤器。

#### AI 工具插件

- 把服务端能力包装成 AI 可调用工具；
- 自动生成工具说明；
- v1 不启用审批和权限细分，保留接口。

#### 维护插件

- 清理；
- 备份；
- 报告；
- 通知；
- Webhook；
- 数据迁移。

### 8.2 服务端插件运行时

## 10. 命令结果正则提取与筛选

### 10.1 设计目标

Web 终端需要允许操作员对命令输出做正则提取。

它必须支持两种作用范围：

1. **当前已显示的输出**；
2. **下一次即将返回的命令结果**。

同时应支持：

3. **持续过滤**：直到手动关闭为止，对所有新结果生效。

### 10.2 三种模式

#### Filter Current

对当前屏幕中已经有行进行筛选：

- 输入正则；
- 只显示匹配行；
- 可高亮匹配；
- 可隐藏非匹配行；
- 原始输出不被修改。

#### Filter Next

对下一次将要返回的命令结果自动应用正则：

- 设置规则；
- 下一条命令输出返回后自动筛选；
- 规则可只生效一次；
- 适合 AI 或操作员预置提取条件。

#### Sticky Filter

持续过滤：

- 对所有后续命令结果生效；
- 直到手动关闭；
- 规则可保存命名。

### 10.3 过滤能力

- 普通正则；
- 忽略大小写；
- 多行模式；
- 反转匹配；
- 只保留匹配行；
- 只显示捕获组；
- 高亮匹配；
- 结果计数；
- 正则错误提示。

### 10.4 命名规则

可保存为：

```text
named filters:
  - ipv4
  - url
  - email
  - error-lines
  - windows-path
  - linux-path
```

服务端插件可以保存这些规则，客户端可以本地保存常用规则。

### 10.5 原始结果不可变

正则提取只改变显示视图。

- `result.raw` 始终完整；
- `result.filtered` 是派生视图；
- 下载、导出、AI 调用默认拿原文，除非明确要求过滤结果；
- 过滤不能导致数据丢失。

## 11. 下发 Python 代码注释剥离

### 11.1 强制规则

所有由服务端发往植入物执行的 Python 代码，在离开服务端之前必须统一剥离注释，无一例外。

适用范围：

- `implant_plugins/` 下的插件代码；
- 客户端上传的本地 `.py` 脚本；
- `python.exec` 的 raw Python 片段；
- 协议升级脚本；
- 服务端临时生成的控制代码；
- 单阶段载荷中携带的 Python 执行代码；
- 任何未来新增的下发代码通道。

### 11.2 剥离方式

- 使用 Python `tokenize` 识别真正的 `#` 注释；
- 不误删字符串、f-string、三引号字符串中的 `#`；
- 保留换行与缩进，尽量保持源码行号；
- 不允许使用简单正则粗暴替换；
- 语法解析失败时拒绝下发；
- 服务端存储的源码可以保留注释，只在“下发出口”剥离。

### 11.3 流程

```text
插件/脚本/raw 源码
  → 服务端 CodeDeliveryPipeline
  → tokenize 去注释
  → 编译校验
  → 计算 stripped_hash
  → 加密
  → 下发植入物
```

### 11.4 审计

记录：

- 原始 hash；
- 剥离后 hash；
- 剥离字符数/行数；
- 来源类型；
- 任务 ID；
- 实际下发时间。

植入物只接收剥离后的代码。

## 12. 插件版本与生命周期（v1）

### 12.1 生命周期

```text
编写
  → 放入插件目录
  → 服务端启动或热重载扫描
  → 读取 manifest
  → 尝试加载
  → 成功注册
  → 失败打印错误
  → 执行
  → 审计
  → 修改/替换后热重载
```

### 12.2 版本与 hash

- 建议每个插件包含版本和 hash；
- 版本不可变；
- 修改插件生成新版本；
- 植入物缓存只在内存；
- 不把插件写盘。

### 12.3 v1 不做签名与信任校验

- 插件目录即信任边界；
- 不需要签名；
- 不需要多发布者；
- 加载失败只打印错误；
- 加载失败时保留旧版本继续运行；
- 服务端插件可被客户端读取、修改、替换并热重载。

## 13. 风险与审批

| 等级 | 插件示例 | 策略 |
|---|---|---|
| R0 | system.info、fs.list、lps/wps | 允许 |
| R1 | fs.read、netstat | v1 默认放行并审计 |
| R2 | fs.write、upload、download、file edit | v1 默认放行并审计 |
| R3 | python.exec、proxy、process kill | v1 默认放行并审计 |

## 14. 失败与恢复

### 14.1 插件失败

- 捕获异常；
- 返回错误结构；
- 不影响其他插件任务；
- 不影响 Beacon 运行时；
- 完整错误进入结果。

### 14.2 上传/下载失败

- 记录已传输块；
- 支持续传；
- hash 不匹配则失败；
- 用户可以选择重试；
- 不清空已有元数据。

### 14.3 文件编辑冲突

- 保存前比较 hash；
- 远端已变化则提示冲突；
- 可以重新加载或强制覆盖；
- 强制覆盖需要审批/明确确认。

### 14.4 代理失败

- 隧道标记失败；
- 释放端口；
- 不影响其他隧道；
- 记录原因；
- 客户端可重新创建。

### 14.5 正则错误

- 不执行无效正则；
- 显示解析错误；
- 当前输出保持不变；
- 不破坏已显示结果。

## 15. 默认决策

1. 植入插件与服务端插件统一为 Python 插件。
2. 插件是能力单元，不是 Shell 包装。
3. 平台实现不同则拆分命令：
   - Linux 用 `l` 前缀；
   - Windows 用 `w` 前缀。
4. `ps` 拆为 `lps` 和 `wps`。
5. 跨平台 Python 实现保留统一命令名。
6. 旧 `exec`/`shell` 移除，改为 `python.exec`。
7. 所有文件、进程、网络、代理、上传、下载、截图能力插件化。
8. 支持客户端选择本地 `.py` 文件下发执行。
9. 支持 Web 文件编辑：打开、编辑、保存、远程原子写回。
10. 支持 Web 目录浏览：路径、列表、排序、搜索、上传、下载、编辑。
11. 命令输入支持补全与历史。
12. 命令输出支持正则筛选：
    - 当前结果；
    - 下一条结果；
    - 持续过滤。
13. 原始结果永不因过滤而丢失。
14. 大文件与大结果分块，不截断。
15. v1 插件目录即信任，不做签名；保留版本与 hash。
16. 服务端插件可注册新命令、API、代理网关、结果处理器、AI 工具。
17. 高风险插件 v1 默认放行，保留审批接口。
18. 人类 Web、AI 和插件目录使用统一能力模型。

## 16. 设计验收问题

1. 是否所有业务能力都由插件提供？
2. 是否平台专用命令按 `l` / `w` 前缀拆分？
3. 是否 `ps` 已拆成 `lps` / `wps`？
4. 是否跨平台代码只保留一份通用插件？
5. 是否插件不依赖 Shell？
6. 是否插件代码不写盘？
7. 是否本地 `.py` 文件可以下发并内存执行？
8. 是否 Web 支持目录浏览？
9. 是否 Web 支持打开、编辑、保存文件？
10. 是否保存时检测文件冲突？
11. 是否下载支持分块与 hash？
12. 是否上传支持目标路径与覆盖确认？
13. 是否代理由植入插件和服务端网关共同完成？
14. 是否命令补全按 Beacon 平台过滤？
15. 是否支持当前输出正则筛选？
16. 是否支持下一条结果自动正则筛选？
17. 是否支持持续过滤模式？
18. 是否正则过滤不修改原始结果？
19. 是否有插件 manifest、版本、加载错误处理和热重载机制？
20. 是否服务端插件可扩展运行时能力并写审计？

---

## 17. 最终总结

插件体系的设计灵魂是：

> **植入物只提供执行内核，服务端只提供控制与调度；所有业务能力由插件提供；平台差异用 `l` / `w` 命令显式拆分；文件、代理、上传下载、脚本执行、文件编辑、目录浏览和正则提取都成为一等能力。**

一句话：

> **跨平台的用共通插件，平台不同的用 `l` / `w` 分家；业务命令不套 Shell，插件在内存里干活，Web 负责看见与操作，原始结果永远不丢。**
