## 0. 一句话定义

**植入物是一个请求远端 Python 代码、在本地执行 Python 代码、把结果带回远端服务器的极简远程执行内核。**

它的全部核心动作可以压缩成一句话：

```text
拉代码 → exec 执行 → 收结果 → 回传结果 → 再拉代码
```

除此之外的东西 —— 文件、进程、网络、截图、持久化、协议切换、结果处理 ——
都应当被视为“可执行的 Python 能力”，而不是植入物内核的硬编码业务逻辑。

## 1. 植入物的第一性原理

### 1.1 代码就是任务

一个任务不是“执行某个固定命令”，而是一段服务端下发的 Python 代码。

- 代码由服务端产生；
- 代码由植入物接收；
- 代码在植入物内存中被 `exec`；
- 执行结果由植入物返回；
- 代码可以调用运行时全局能力；
- 代码可以改变运行时全局状态。

### 1.2 植入物只做“拉、跑、回”

植入物内核的职责边界只有四件事：

1. **拉取**远端待执行 Python 代码；
2. **执行**代码；
3. **暂存**执行结果；
4. **回传**结果并继续下一轮。

它不应该：

- 内置 `ls`、`cat`、`ps`、`netstat` 等业务命令；
- 依赖 Shell；
- 把代码写盘；
- 把插件做成固定白名单；
- 把某一种传输协议写死为唯一通道。

### 1.3 拉取模型，而不是服务端主动推送模型

植入物是主动方：

- 连接服务端；
- 报告已有结果；
- 请求所有待执行代码；
- 拿到代码后断开连接；
- 本地执行；
- 到时间后再次主动连接。

即使服务端无法主动连接植入物，植入物也能工作。

### 1.4 执行和连接解耦

连接只负责“交换数据”，不负责“等待执行完成”。

代码在本地并行运行，连接可以关闭。  
执行完成后再建立下一次连接。

### 1.5 多任务并行，无默认超时

- 一次拉取可以拿到多段 Python 代码；
- 每段代码是一个独立任务；
- 不同任务可以并行执行；
- 任务默认没有执行超时；
- 长时间运行任务不会因为“定时器”被强制结束；
- 只有总控端通过下发的控制代码或控制能力主动终止任务。

这里的“没有超时”是逻辑语义，不意味着放弃资源治理。  
内存、结果大小、并发数、取消机制仍然需要边界。

### 1.6 全局运行时必须是“可修改的”

载荷端需要极高的灵活性，因此必须允许 `exec` 的代码：

- 读取运行时全局对象；
- 调用全局函数；
- 修改全局变量；
- 替换或升级通信协议；
- 更新通信密钥；
- 调整回连参数；
- 注册新的工具函数；
- 修改协议选择策略。

这是协议切换、密钥轮换、运行时热升级的基础。

但全局可修改不等于“放任覆盖核心对象”：

- 每个任务有独立本地变量区；
- 插件显式使用 `global` 或运行时 API 才能修改共享全局；
- 全局对象可读、可调用、可控写；
- 任务局部变量不会意外污染其他任务。

## 2. 三层总体结构

```text
客户端层
  ├── Web 可视化客户端
  ├── CLI / 自动化
  └── AI Operator

服务端层
  ├── 任务队列 / 代码提供器
  ├── 结果接收器
  ├── 多协议 Gateway
  ├── 运行时控制面
  ├── 插件 / 代码仓库
  └── 审计与策略

植入物层
  ├── 最小启动器
  ├── 传输插件管理器
  ├── 协议插件
  ├── 全局运行时
  ├── 任务注册表
  ├── 执行器
  ├── 结果队列
  └── 控制代码执行器
```

### 2.1 服务端和植入物是主体

客户端可以不存在。  
即使没有 Web、没有 AI、没有命令行，服务端和植入物仍然可以运行。

### 2.2 客户端只是观察与控制

客户端负责：

- 看状态；
- 发起任务；
- 审阅结果；
- 进行审批；
- 查看协议与路径；
- 与 AI 协同。

客户端不保存权威状态，也不能绕开服务端策略。

## 3. 植入物内部思想模型

植入物内部可以理解为七个部件：

### 3.1 启动器

最小启动器只负责：

- 启动运行时；
- 读取初始配置；
- 加载载荷生成时绑定的协议；
- 发起第一次连接；
- 进入拉取循环。

它不包含业务能力。

### 3.2 传输插件管理器

负责：

- 加载当前协议；
- 建立连接；
- 发送封装包；
- 接收封装包；
- 关闭连接；
- 检查健康度；
- 切换协议；
- 维护备用协议；
- 在失败时按策略回退。

### 3.3 协议插件

协议插件负责“怎么把加密包从 A 送到 B”。

预设协议：

```text
起始协议由监听器和载荷生成时决定，植入物不内置默认协议

可加载协议：
TCP
UDP
HTTP
HTTPS
DNS
ICMP
```

后续可扩展：

```text
WebSocket
TLS
mTLS
HTTP/2
DoH
DoT
QUIC
SMB / named pipe
其他授权环境允许的承载
```

协议插件不理解任务、插件或结果语义。

### 3.4 全局运行时

全局运行时是所有任务共享的“能力台面”。

它保存：

- Beacon 身份；
- 当前协议对象；
- 备选协议；
- 通信密钥；
- 加密/解密封装函数；
- 任务注册表；
- 运行中任务；
- 已完成结果队列；
- 回连时间参数；
- 自适应回连状态；
- 日志/进度上报函数；
- 结果构造器；
- 控制函数。

全局运行时是**可读、可调用、可修改**的，尤其允许代码升级通信协议和密钥。

### 3.5 任务注册表

记录：

- 任务 ID；
- 代码片段；
- 开始时间；
- 运行状态；
- 所属协议；
- 是否已汇报；
- 取消标记；
- 结果队列；
- 运行中任务的控制句柄。

总控端可以下发 Python 控制代码来查询和操作这张表。

### 3.6 执行器

负责：

- 为每个代码片段创建执行环境；
- 并行启动任务；
- 捕获标准输出和错误；
- 捕获异常；
- 把结果写入结果队列；
- 在任务结束时更新任务注册表；
- 不因为任务未完成而阻塞连接循环；
- 不强制设置默认执行超时。

### 3.7 结果队列

保存：

- 已完成结果；
- 任务 ID；
- 输出；
- 错误；
- 完成时间；
- 元数据；
- 是否需要分块；
- 是否已收到服务端确认。

结果在未确认前不能被丢弃。

## 4. 载荷下发思想

### 4.1 两种交付表现

植入物的初始投递可以表现为：

1. **单载荷入口**
   - 一段 Python 代码整体进入执行；
2. **多载荷入口**
   - 一个入口携带多段 Python 代码或一个代码批次。

无论入口是单载荷还是多载荷，执行本质都归一为：

> 把一段或多段 Python 代码交给 `exec`。

不存在“第一阶段状态机”和“第二阶段状态机”的双载荷架构。

### 4.2 两种搬运方式

多载荷入口可以有两种常见搬运方式：

#### Echo 方式

```text
echo "<python代码>" | python
```

#### Curl 方式

```text
curl "<地址>" | python
```

两者只是搬运方式不同，执行本质相同：

```text
Python 代码进入内存 → exec 执行
```

### 4.3 单阶段的真正含义

单阶段不是“只有一个网络包”，而是：

- 不存在服务端维护的“第一阶段载荷 → 第二阶段载荷”的状态机；
- 不存在必须先安装第一阶段再等待第二阶段的架构依赖；
- 后续所有代码都通过任务队列获得；
- 每一次任务都是独立可执行代码片段；
- echo 和 curl 只是进入运行时的方法，不是两个阶段。

### 4.4 任务批次的来源

任务代码可以来自：

- 服务端任务队列；
- 服务端插件代码仓库；
- 服务端临时控制代码；
- 服务端针对某个 Beacon 生成的特殊代码。

植入物不关心代码来源，只关心：

- 代码是否完整；
- 是否通过解密和校验；
- 是否有任务 ID；
- 是否可执行。

所有收到的 Python 代码已经在服务端完成注释剥离。  
植入物不负责、也不需要再次处理注释。

## 5. 执行队列与并行任务

### 5.1 一轮连接的数据交换

一轮连接的顺序：

```text
1. 植入物连接服务端
2. 植入物上报上次已完成但未确认的结果
3. 服务端返回确认
4. 植入物请求当前所有待执行代码
5. 服务端一次性返回一批待执行代码
6. 植入物关闭连接
7. 植入物本地并行执行代码
```

### 5.2 为什么拿完代码就断开

因为连接不等于执行会话。

- 连接只需要传输数据；
- 执行可以在断网状态下继续；
- 代码执行完成后重新连接；
- 这样更适合 UDP、DNS、HTTP 等短连接/请求-响应协议；
- 服务端不需要维持大量长时间空闲连接。

### 5.3 并行执行

每个代码片段都是一个独立任务。

- 多段代码可以同时开始；
- 长任务不会阻塞其他任务；
- 没有默认执行超时；
- 一个任务失败不影响其他任务；
- 任务注册表统一追踪状态；
- 结果队列统一收集结果。

### 5.4 运行中任务的控制

总控端应该能够下发一段 Python 控制代码，查询：

- 当前有哪些运行中任务；
- 每个任务的 ID；
- 每个任务的开始时间；
- 每个任务的协议/来源；
- 是否有已完成但未回传的结果。

并能够下发控制代码：

- 取消指定任务；
- 取消全部任务；
- 标记任务终止；
- 清理结果队列；
- 切换协议；
- 轮换密钥；
- 修改回连参数。

“终止任务”不是靠关掉整个连接，而是对任务注册表发指令。

## 6. 全局运行时与任务局部变量

### 6.1 双层模型

植入物执行代码时采用双层变量模型：

```text
全局运行时 G
  —— 所有任务共享
  —— 包含通信、密钥、协议、任务表、结果队列、控制函数
  —— 可读、可调用、可修改

任务局部区 L
  —— 每个任务独立
  —— 普通赋值默认写这里
  —— 任务结束可整体丢弃
  —— 不污染其他任务
```

执行语义类似于：

```text
exec(code, G, L)
```

### 6.2 为什么要两层

只有全局：

- 插件容易互相覆盖；
- 普通变量可能破坏通信层；
- 并发执行时状态混乱。

只有局部：

- 不能切换协议；
- 不能更新密钥；
- 不能修改运行时函数；
- 灵活性不够。

所以必须是两层：

- **局部默认隔离**；
- **全局显式修改**。

### 6.3 局部变量规则

- 普通赋值、函数定义、临时变量默认进入任务局部区；
- 任务结束即销毁；
- 同一个任务内部的变量可以自由使用；
- 并发任务之间的局部变量互不干扰。

### 6.4 全局修改规则

代码需要修改运行时全局时，可以通过：

- Python 的 `global` 声明；
- 运行时提供的显式全局设置函数；
- 直接修改全局运行时中的可变对象；
- 控制代码专用接口。

允许修改的典型全局对象：

- 当前协议；
- 备用协议；
- 通信密钥；
- 加密函数；
- 回连间隔；
- 抖动参数；
- 任务完成后的等待时间；
- 协议切换函数；
- 结果处理函数；
- 任务注册表。

### 6.5 灵活性原则

运行时全局暴露得越充分，插件越灵活。

因此：

- 不要隐藏通信对象；
- 不要隐藏协议对象；
- 不要隐藏任务注册表；
- 不要隐藏结果队列；
- 不要隐藏回连调度器；
- 不要隐藏密钥管理器；
- 不要隐藏控制函数；
- 但要用“显式全局修改”而不是“无意覆盖”。

### 6.6 未来扩展能力

有了可修改全局运行时，未来可以实现：

- UDP → HTTPS 协议热切换；
- 密钥轮换；
- 传输插件热加载；
- 新的结果编码；
- 新的心跳算法；
- 新的回连策略；
- 动态调整并发数；
- 动态修改任务调度策略；
- 远程升级运行时能力；
- 远程查询/取消任务。

## 7. 回连周期思想

### 7.1 任务完成后的等待与结果聚合窗口

当任意一个 Python 代码执行完成：

```text
任务完成
  → 结果进入结果队列
  → 启动一个可配置的“完成回报延迟窗口”（默认 5 秒）
  → 如果在窗口内又有其他 Python 代码完成
  → 重置窗口，从最后一次完成重新计时
  → 窗口安静到期
  → 建立连接，将所有已完成结果一起上报
  → 获取新代码
  → 关闭连接
```

这个“5 秒”不是协议常量，而是运行时全局变量，可被任务代码修改。

核心效果：

- 第一个任务完成时启动 5 秒窗口；
- 5 秒内其他任务完成时，窗口重置；
- 每次新完成都重新开始计算 5 秒；
- 目的是让短时间内连续完成的结果一起回传；
- 不在每个结果完成时分别回连；
- 减少连接次数和流量碎片；
- 所有已完成结果在同一轮连接中按顺序批量上传。

### 7.2 如果还有任务没有完成

如果结果聚合窗口到期，但仍有任务没有执行完成：

```text
仍存在运行中任务
  → 不等待所有任务完成
  → 按“默认回连时间”建立连接
  → 上报当前已完成结果
  → 获取新代码
  → 关闭连接
  → 运行中任务继续自行执行
```

如果在这之前又有新的任务完成，则仍然按 7.1 的规则重置 5 秒结果聚合窗口。

这保证：

- 长任务不阻塞已完成结果回传；
- 已完成结果不会因为其他长任务而无限延迟；
- 新代码可以继续被拉取和执行；
- 没有默认执行超时；
- 已完成结果和未完成任务的边界清晰。

### 7.3 回连触发条件

植入物回连可以由以下条件触发：

1. 有任务完成，且最后一次完成后经过安静窗口，完成回报延迟到期；
2. 没有完成结果，但默认回连时间到期；
3. 服务端曾在上一轮要求下一次更快回连；
4. 有控制代码要求立即回连；
5. 协议切换或密钥轮换需要确认；
6. 当前链接失效后按回退策略重连。

### 7.4 结果确认

- 服务端收到结果后返回确认；
- 植入物收到确认后从结果队列删除；
- 未确认的结果继续保留；
- 下一轮重新上报；
- 服务端按任务 ID 去重。

## 8. 自适应回连速度

### 8.1 核心思想

回连速度应该随“任务下发次数”变化，而不是随“某一批任务里包含多少段代码”变化。

这里必须明确区分：

- **任务下发次数**：一段时间内总控端向某个 Beacon 产生任务的次数/批次次数；
- **单批代码数量**：一次下发里包含几段 Python 代码；
- **运行中代码数量**：当前正在并行执行的代码段数量。

本设计用于调节心跳/回连节奏的主指标是：

> **一段时间内任务下发的次数与频率。**

例如：

- 10 分钟内连续下发了 10 次任务 → 说明控制端正在高频操作，回连应该逐步加快；
- 连续一段时间没有任何任务下发 → 说明目标空闲，回连应该逐步放慢；
- 一批里发了 10 段代码，但只发生了一次下发 → 这不等于 10 次下发，不能仅因为批量大就误判为高频操作；
- 当前有很多代码在运行，但没有新的任务下发 → 也不能因此持续保持高频回连，仍需按“下发频率”向慢端衰减。

本文把“心跳”和“回连”视为同一调度周期的两个表述：  
一次回连通常同时承担上报结果、获取新任务、维持存在感的功能。

回连间隔规则：

- 任务下发次数变多 → 回连间隔逐步缩短；
- 任务下发次数变少 → 回连间隔逐步延长；
- 最快端和最慢端都可配置；
- 回连时间必须带可配置的随机抖动；
- 自适应依据是任务下发历史，而不是单次批量大小。

### 8.2 默认参数

采用以下默认思想值：

| 参数 | 默认值 | 含义 |
|---|---:|---|
| 任务完成回报延迟 | 5 秒 | 首个结果完成后启动安静窗口；窗口内每次新完成都会重置计时，最后批量回传 |
| 快速回连端 | 5 秒 | 最短等待时间，即回连频率上限 |
| 缓慢回连端 | 10 分钟 | 最长等待时间，即回连频率下限 |
| 抖动范围 | 可配置 | 在回连间隔附近上下波动 |
| 任务执行超时 | 无 | 默认不因超时终止任务 |
| 初始协议 | 由监听器/载荷决定 | 载荷生成时绑定，植入物不硬编码默认协议 |

需要特别说明：

- “回连频率上限 = 5 秒”对应“最短回连间隔 = 5 秒”；
- “回连频率下限 = 10 分钟”对应“最长回连间隔 = 10 分钟”。

### 8.3 加速与减速思想

#### 任务下发频繁 → 加快

当一段时间内出现以下情况时，回连间隔向快速端靠近：

- 连续多次收到新的任务下发；
- 任务下发频率高于当前观察窗口的平均值；
- 例如 10 分钟内连续发生 10 次任务下发；
- 服务端明确标记该 Beacon 处于高频操作期；
- 控制代码要求加快回连。

加快的对象是**回连频率**，表现为**回连间隔缩短**。

#### 任务下发稀疏 → 放慢

当一段时间内出现以下情况时，回连间隔向缓慢端靠近：

- 连续一段时间没有任何新的任务下发；
- 任务下发频率持续低于观察窗口平均值；
- 多轮连接只拿到空任务；
- 没有控制指令要求保持高频；
- 服务端建议降低频率。

放慢的对象是**回连频率**，表现为**回连间隔延长**。

注意：

- 单批代码很多但只下发了一次：不能仅按这一批的大小判断为“高频”；
- 大量任务正在运行但没有新下发：回连仍应按下发频率逐步放慢；
- 任务下发次数是主信号，运行中任务数量、结果数量和批量大小只能作为辅助信号。

### 8.4 抖动

每次实际等待时间不是固定值，而是在计算出的回连间隔附近波动：

```text
实际等待 = 基础间隔 × (1 ± 随机抖动范围)
```

抖动范围必须可配置。

抖动目的：

- 避免固定时间指纹；
- 避免大量 Beacon 同步回连；
- 降低流量周期性。

### 8.5 本地全局变量化

以下参数都应当是全局运行时变量：

- 完成回报延迟；
- 快速回连间隔；
- 缓慢回连间隔；
- 抖动范围；
- 当前自适应速度；
- 连续空闲轮数；
- 最近一段时间任务下发次数；
- 最近一段时间任务下发频率；
- 任务下发频率的滑动窗口；
- 下一次计划回连时间。

这样控制代码可以随时调整，不需要重新部署植入物。

## 9. 协议插件思想

### 9.1 起始协议由监听器和载荷决定

植入物不预设“默认使用 UDP”或任何其他协议。

协议信息来自载荷生成阶段：

```text
服务端先创建监听器
  → 确定协议、地址、端口、密钥、回连策略
  → 生成与该监听器匹配的单阶段载荷
  → 植入物启动时读取载荷内绑定的协议配置
  → 加载对应协议插件
  → 按监听器配置发起第一次连接
```

因此：

- UDP 只是支持的协议之一；
- TCP、HTTP、HTTPS、DNS 也可以作为起始协议；ICMP v1 暂不实现；
- 起始协议由载荷生成时的监听器和策略决定；
- 植入物核心不硬编码默认协议；
- 同一个植入物可以在运行中升级或切换到其他协议；
- 服务端先生成监听器，再生成对应植入物，这个顺序是固定的。

### 9.2 协议插件统一职责

每个协议插件都只负责：

- 连接；
- 发送；
- 接收；
- 关闭；
- 健康检查；
- 分片/重组适配；
- 重传策略；
- 协议特定元数据。

它不负责：

- 任务解释；
- 插件执行；
- 结果解析；
- 风险策略；
- 审批。

### 9.3 预设协议

```text
udp     轻量、请求-响应、弱连接状态
tcp     稳定流式，适合大结果
http    请求-响应，容易穿过普通 Web 环境
https   HTTP + TLS 外观，适合口令/信令
dns     分片信令，适合受限网络
icmp    v1 暂不实现，保留插件接口
```

未来扩展：

```text
websocket
tls
mtls
http2
doh
dot
quic
smb / named pipe
```

### 9.4 协议切换

协议切换应由全局运行时管理，而不是写死在某段代码里。

切换思想：

```text
当前协议保持可用
  → 准备候选协议
  → 使用候选协议建立探测连接
  → 验证身份、加解密、任务拉取、结果上传
  → 成功则提交切换
  → 失败则回滚到旧协议
```

切换期间：

- 任务继续执行；
- 结果队列继续保留；
- Beacon 身份不变；
- 任务 ID 不变；
- 不重放已完成任务；
- 不丢失未确认结果。

### 9.5 植入物协议升级

植入物必须支持运行中协议升级。

示例：

```text
当前：TCP 载荷
  → 服务端创建 HTTPS 监听器
  → 服务端通过任务下发一段 Python 升级脚本
  → 升级脚本在植入物内存中加载 HTTPS 协议插件
  → 使用 HTTPS 监听器建立探测连接
  → 完成一次身份校验、任务拉取、结果上传验证
  → 验证成功，提交协议切换
  → 新协议成为主路径
  → 原 TCP 可保留为备用路径或按策略关闭
```

升级过程中必须保持：

- Beacon 身份不变；
- 任务 ID 不变；
- 运行中任务继续执行；
- 结果队列不丢；
- 未确认结果可继续通过旧协议回传；
- 升级失败自动回滚；
- 升级代码只在内存中执行，不落盘；
- 升级脚本必须签名、加密、可审计。

### 9.6 协议升级与回退策略（v1 范围）

v1 不实现 random / weighted-random 随机协议策略。

v1 只实现明确的 A → B 协议升级与回退：

```text
初始协议 A（由载荷/监听器决定）
  → 服务端下发 Python 升级任务
  → 植入物连接并验证目标协议 B
  → B 成功：B 成为当前协议
  → B 连续失败或连续断开达到 30 次心跳
  → 自动回退到 A
```

全局运行时保存：

- 初始协议 A；
- 当前协议 B；
- 回退目标 A；
- 连续失败次数；
- 失败阈值（默认连续 30 次心跳）；
- 当前协议状态；
- 上一次切换原因。

未来如需随机策略，再增加：

- fixed；
- random；
- weighted-random。

v1 不做。

### 9.7 新增协议

新增协议只需要提供：

- 协议插件；
- 服务端对应 Gateway；
- 能力描述；
- 测试用例；
- 配置 schema；
- 安全说明；
- 协议升级脚本；
- 回退与健康检查策略。

不需要修改任务层、插件执行层、结果层或 Web 业务层。

## 10. 加密、压缩与混淆

### 10.1 传输协议不是安全边界

即使走 HTTPS/TLS，任务和结果仍必须应用层加密。

### 10.2 封装包

统一封装应包含：

- 协议版本；
- 消息类型；
- 会话信息；
- 任务/结果 ID；
- 序号；
- 压缩标记；
- 加密数据；
- 完整性标签；
- 随机填充。

### 10.3 混淆

- 随机 padding；
- 长度掩码；
- 随机分片；
- 请求/响应时间抖动；
- 协议外观适配；
- 心跳与背景流量；
- DNS 专用编码；ICMP 在 v1 不实现。

### 10.4 密钥与切换

- 主密钥；
- 会话密钥；
- 密钥版本；
- 轮换窗口；
- 旧 key 过渡；
- 全局运行时暴露密钥管理器函数；
- 控制代码可触发轮换；
- 未确认结果仍用旧会话可解密窗口返回。

## 11. 服务端总体思想

### 11.1 代码提供器

服务端负责为每个 Beacon 准备待执行 Python 代码：

- 普通任务代码；
- 控制代码；
- 插件代码；
- 协议升级代码；
- 密钥轮换代码。

### 11.2 结果接收器

- 接收结果；
- 去重；
- 校验完整性；
- 确认接收；
- 写入任务时间线；
- 大结果转 artifact；
- 不截断完整输出。

### 11.3 多协议 Gateway

- 每个协议有独立 Gateway；
- Gateway 只处理传输和封装；
- 所有 Gateway 使用同一任务语义；
- 协议失败不影响其他协议；
- 路由选择器负责选择当前活跃协议。

### 11.4 控制面

服务端可以下发控制代码：

- 查看运行中任务；
- 终止指定任务；
- 终止全部任务；
- 查询结果队列；
- 修改回连参数；
- 切换协议；
- 触发密钥轮换；
- 读取运行时状态。

控制代码也应有审计、权限和风险级别。

### 11.5 路由选择

服务端决定建议路径：

- 当前协议；
- 备用协议；
- 下次建议回连时间；
- 是否还有更多代码；
- 任务优先级；
- 结果上传优先。

植入物仍保有本地决策权，但服务端可以提供更优建议。

## 12. Web 与 AI 的角色

### 12.1 Web

Web 是驾驶舱：

- 查看 Beacon；
- 查看任务；
- 查看完整结果；
- 管理插件；
- 生成单阶段载荷；
- 查看协议路径；
- 审批高风险动作；
- 查看 AI 计划。

AI 是第二位操作员：

- 读取能力目录；
- 生成执行计划；

- 解释结果；
- 提出协议切换建议；
- 不能绕过审批；
- 不能直接连接植入物；
- 不能自行获得通信密钥。

### 12.3 人机共用能力平面

- 人类和 AI 使用同一任务模型；
- 同一插件目录；
- 同一风险等级；
- 同一审批中心；
- 同一审计账本；
- 同一结果展示。

## 13. 安全与灵活性边界

### 13.1 灵活性的边界

灵活性不等于无约束。

允许代码修改全局运行时，是为了：

- 协议升级；
- 密钥轮换；
- 通信策略调整；
- 运行时热更新。

但必须：

- 记录全局状态变化；
- 对高风险全局修改进行审批；
- 保留旧运行时快照或回滚路径；
- 不允许通过全局修改绕过审计。

### 13.2 无盘边界

植入物自身：

- 不写代码文件；
- 不写临时脚本；
- 不写 `__pycache__`；
- 不把插件缓存写盘；
- 不把结果队列写盘。

用户明确要求的目标文件操作除外。

### 13.3 无 Shell 边界

- 不通过 Shell 执行命令；
- 常见命令用 Python 插件直接实现；
- 外部进程只作为显式能力；
- 参数化、非交互、可审计。

## 14. 失败与恢复

### 14.1 连接失败

- 按回连策略重试；
- 优先尝试当前协议；
- 失败后使用备用协议；
- 不丢结果队列；
- 不重复执行已完成任务。

### 14.2 代码执行失败

- 任务标记失败；
- 错误进入结果队列；
- 不影响其他任务；
- 不杀死运行时；
- 控制端可见完整错误。

### 14.3 任务长期不结束

- 默认不超时；
- 控制代码可查询运行中任务；
- 控制代码可终止任务；
- 结果队列仍然可以上报；
- 不阻塞新任务拉取。

### 14.4 结果未确认

- 保留在结果队列；
- 下轮重传；
- 服务端按任务 ID 去重；
- 不重复执行任务。

### 14.5 协议切换失败

- 保持旧协议；
- 回滚全局协议状态；
- 保留任务与结果；
- 记录失败原因；
- 不造成 Beacon 身份变化。

## 15. 任务状态思想

```text
已获取 → 已启动 → 运行中 → 完成
                     ↘ 失败
                     ↘ 已取消
                     ↘ 结果未确认
                     ↘ 结果已确认
```

任务没有默认超时状态。  
“超时”不是默认动作，“取消”是明确控制动作。

## 16. 协议与任务关系

```text
任务与协议无关
结果与协议无关
插件与协议无关
运行时身份与协议无关

协议只决定：
  - 数据怎么走
  - 分片怎么做
  - 重传怎么做
  - 外观像什么
```

切换协议不改变任务 ID。  
切换协议不重新创建 Beacon。  
切换协议不改变结果内容。

## 17. 总体数据流

```text
服务端任务队列
    ↓ 代码批次
植入物请求
    ↓ 解密 / 验证
全局运行时 + 任务注册表
    ↓ 并行 exec
执行结果
    ↓ 结果队列
等待完成回报延迟（默认 5 秒）
    ↓
重新连接
    ↓ 上传结果 + 拉取新代码
服务端结果接收 / 确认
    ↓
下一轮
```

## 19. 设计验收问题

每个实现决策都应回答：

1. 它是否仍然只是“请求 Python 代码并 exec”？
2. 它是否引入了不必要的磁盘写入？
3. 它是否引入了不必要的 Shell？
4. 它是否把业务能力硬编码进核心？
5. 它是否允许一个代码片段并行执行而不阻塞其他代码？
6. 它是否错误地给任务增加了默认超时？
7. 它是否允许总控端下发控制代码查看和终止任务？
8. 它是否区分了任务局部变量和共享全局变量？
9. 它是否允许显式修改全局协议、密钥和回连参数？
10. 它是否把协议做成了可插拔能力？
11. 它是否把传输和业务语义分离？
12. 它是否支持一次拉取多段代码后断开连接？
13. 它是否支持任务完成后延迟回连？
14. 它是否支持任务未完成时按默认间隔回连？
15. 它是否让回连间隔随“任务下发次数/频率”自适应，而不是误用单批代码数量？
16. 它是否让回连上下限、抖动、5 秒延迟都可配置？
17. 它是否在多个任务连续完成时重置 5 秒窗口，并批量回传结果？
18. 它是否能切换 UDP / TCP / HTTP / HTTPS / DNS（ICMP v1 不实现）？
19. 它是否保护未确认结果不丢失？
20. 它是否让人类和 AI 使用同一任务与审批语义？
21. 它是否保持 Beacon 身份不随协议切换而改变？

## 20. 最终总结

植入物的思想不是“功能很多”。

植入物只做一件事：

> **从远端请求 Python 代码，`exec` 执行，保存结果，按策略回传。**

其余的一切能力都从这里生长出来：

- 常见命令 → Python 代码插件；
- 多任务 → 并行执行；
- 任务查看与终止 → 控制代码；
- 协议切换 → 可修改全局运行时 + 协议插件；
- 密钥升级 → 可修改全局运行时；
- 自适应回连 → 全局调度变量；
- 无盘/无 Shell → 内存执行和 Python 原生能力；
- 人类和 AI → 服务端能力平面的不同操作者。

最终的设计灵魂是：

> **核心极简，运行时极活，边界极硬，协议极松，任务并行，回连自适应。**

其中“回连自适应”的准确定义是：

> **按一段时间内任务下发的次数和频率调整心跳间隔；任务下发越频繁，回连越快；任务下发越稀疏，回连越慢；多个任务在 5 秒聚合窗口内连续完成时，窗口不断重置，最后把结果集中回传。**

这份文档先作为植入物方向的总体思想基线。  
下一步应该基于它拆出“植入物运行内核”“协议插件”“任务与结果”“控制代码”“服务端任务/回连策略”五个详细设计篇。
